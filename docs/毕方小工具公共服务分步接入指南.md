# 毕方小工具公共服务 3.0 接入指南

## 先看结论

后续新接入以 Rust 为目标，服务配置从授权中心 OAuth 设备授权后的只读接口取得，准确协议与默认值见 [统一接入规范](../skills/bifang-public-services-onboarding/references/integration-contract.md)。客户不手填服务地址/密钥或技术参数表；项目事实自动识别。TypeScript SDK 与示例尚未完整对齐 Updater 1.4.1，不作为新 Rust 字段权威；仅整理规范不发起真实授权或业务实现。

每个小工具在自己的项目中只发一句：

```text
https://github.com/BFTools3666/bifang-operations-assistant.git 帮我接入
```

向导首先通过接入范围门禁，再验证并安装权威 Skill、读取当前项目，仅实施用户选中的统计、更新或两项。仅统计不迁移/删除更新；仅更新不新增/迁移统计。线上部署和其他客户端仍需各自授权。

这句话先触发范围确认；接入记录可在第一门禁后准备，业务代码变更还须通过第二门禁和第三门禁的具体请求明细确认。CloudBase 部署/删除、打包安装、真实 GUI E2E、发布、推送、购买仍是独立动作，必须在对应门禁中执行。

## 门禁顺序

门禁必须按本次已选范围严格串行：1 范围确认 → 2 授权/配置验证 → 3 完整请求明细确认 → 4A UI 确认 → 4B 架构/规范核验 → 4C 编码 → 4D 本地验收。前一步未通过，不进入下一步；两项都接入须当前门禁两项全部通过，不能让成功分支先跨门禁。仅统计无可见 UI 变更只豁免 4A 的人工确认并记录依据，其他检查点不省略。每次转入下一步先核验证据；缺项/未回复/过期不算通过，复用有效证据不重复问。门禁状态写脱敏交接记录，不添加 Profile 字段；旧运维阶段或脚本成功不能代替此链。详见 [门禁信息与放行总表](../skills/bifang-public-services-onboarding/references/integration-contract.md#门禁顺序与放行总表)。

## 第一门禁：确认接入范围

固定首问：“请确认本次接入范围：仅更新、仅统计，还是更新和统计都接入？”只说更新时必须问是否也接统计，只说统计时必须问是否也接更新；同时提两项也先确认。明确答案到达前，不执行来源验证、安装、项目扫描、参数收集或修改。不要默认选两项，也不要把未回复当同意；已有本次门禁明确答案则复用。

确认结果及用户依据写入交接记录，后续参数、变更和验收只覆盖所选服务。未选择的服务保持原状，标为“不在本次范围”；不用“保留日活”替代同意新增统计，也不用统计接入授权删除旧更新。现有联合 Profile 校验若要求未选服务字段，记录工具限制并保留真实草稿，不填假值或强迫全接。

## 第二门禁：授权中心授权与配置获取

第一门禁确认范围后，项目事实自动识别，按 [授权中心设备流程及配置合同](../skills/bifang-public-services-onboarding/references/integration-contract.md#授权中心协议与配置字段) 取得或复用 OAuth 授权。客户只参与必要的浏览器登录、改密/风控确认和批准，不再填写/审批整张参数表。已有有效且权限足够的授权直接复用。

| 范围   | 配置读取                                                                                                                  | 后续                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 仅更新 | 实际获授 `updater:config:read` 后 GET /updater/{project_id}/config，读取 Endpoint、ClientToken                            | 核验更新端点及令牌要求，结合项目事实/默认值接入更新；不查统计配置         |
| 仅统计 | 实际获授 `cloudbase:config:read` 后 GET /cloudbase/{project_id}/config，读取 SecretId、SecretKey、EnvId、Region、Endpoint | 核验环境及日活路由；密钥只用于已授权运维，不放进客户端/日活；不查更新配置 |
| 都接入 | 同一实际获授两个配置 scope 的有效 OAuth access_token 分别读两接口                                                         | 两分支分别校验、实施、验收；一项失败不冒充联合完成                        |

默认 project_id=bifang_tools、scope 按范围取 updater:config:read、cloudbase:config:read 或两者以单个空格连接、超时 10 秒；本地适用登记为 woskill，无 client_secret。生产真实授权中心地址、授权页与登记从运维资料取得，不将 localhost 或占位地址推广为生产默认。应用版本、平台、架构和安装形态自动识别；新稳定流无既有通道时默认 stable，无产品例外默认 service-default，无已实现下载能力默认 capabilities=[]，无语言来源省略 locale；已有产品事实优先，不假定不存在的能力。

申请 scope 只决定授权页预选项；token 响应才是实际获授集合。少选权限停止缺权分支，多选权限不扩大第一门禁范围。旧 `ip:read` 不能查配置，`403 insufficient_scope` 需重新设备授权；刷新默认省略 scope，若发送必须与实际获授集合相同，不能增加或缩减。

通过依据是权限足够的有效授权、所选配置 200 且字段完整、端点/凭据用途核验和项目事实可确定。OAuth Token、Updater ClientToken、CloudBase 密钥不混用，不打印完整响应。配置接口已定义，剩余生产入口、配置录入状态和 CloudBase Endpoint 是否对应日活网关属于部署核验，无法确定才报告必要缺项；不转交客户手填密钥。仅整理规范不运行真实授权。

## 第三门禁：客户端接入方案与请求明细确认

取得并验证所选配置后，自动执行 [第三门禁完整清单](../skills/bifang-public-services-onboarding/references/integration-contract.md#第三门禁客户端接入方案与请求明细确认)。前两门禁事实直接复用，不问已能识别的版本、平台、架构、身份或已定义的默认行为。

| 范围   | 核验与默认值                                                                                                                                                                       | 通过条件                                                                     | 后续步骤                                                                                |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 仅更新 | Rust 配置/请求、九个必填字段来源、调度/UI/强更解除/退出、能力和旧更新清单；已有事实优先，新稳定流无通道用 stable，无例外用 service-default，无下载能力用 []，无语言来源省略 locale | 接入位置和行为明确，能力声明真实，变更及验收计划完整；拟新增能力验证前不声明 | 检查/UI/能力实现 → 替换旧更新 → 本地验证 → 按对应授权做真实检查/制品安装；统计不变      |
| 仅统计 | 准确路由、十字段、Rust 后台启动、UUID v4、应用隔离存储及原子每日门禁；固定 schema_version=2、event=daily_active、sdk_version=3.0.0，Asia/Shanghai 同日一次且失败不补发             | 字段来源、身份/并发/失败/隐私方案明确，管理密钥不入客户端，验收可执行        | 身份与门禁/上报实现 → 本地去重和版本验证 → 按授权登记/部署及真实落库/看板核验；更新不变 |
| 都接入 | 复用两项清单和默认值，再核验真实版本共用、平台映射、保留已有身份、凭据/状态/调度隔离及部分失败                                                                                     | 两项第二门禁、单项方案和联合核验均通过；单项通过不等于联合通过               | 分别实施 → 分项测试 → 相互隔离验证 → 按各自授权完成线上验证                             |

输出具体文件/入口、字段来源、默认值依据、拟修改范围、验收预期和线上依赖，不能虚构目标项目路径或保存敏感值。自动填好所选服务的接入确认单，在回复正文完整展示实际请求 URL、方法、请求头、路径/query/body 字段、必填性、非敏感实际值或动态生成规则、来源/默认值、待补项及实施验收计划；两项均选则分别完整展示。不能只给记录链接，未实施不能称已接入。凭据只展示状态和用途，不回显原值或摘要。技术就绪后必须等待客户明确确认明细；第一门禁选择或浏览器批准不代替此次确认。询问“确认并进入第四门禁／仅确认方案暂不实施／需要调整”，客户可直接授权第四门禁，不必输入阶段编号。已有只读限制不能被简单“确认”解除；未知关键项继续阻断。记录分支确认与实施授权，实质变更重新确认受影响项。完整字段清单与确认规则见 [客户接入确认单](../skills/bifang-public-services-onboarding/references/integration-contract.md#客户接入确认单回复正文必填)。上表仅为技术条件，客户明确确认也是每个分支的必需通过条件。

关键配置/映射未知停止依赖分支；已知尚未登记/部署/发布，在目标及合同明确时可记录为线上依赖并按原授权准备本地实现。仅选一项时按该项过关；联合任务必须两项在当前门禁全部通过才进入下一门禁，不能单分支先推进。此门禁与原 CloudBase 运维阶段 3 分开，不改变独立阶段授权，不表示实现或线上验收完成。

## 第四门禁：客户端本地实施与验收

第四门禁先做 UI 方案与位置确认，再编码：选择更新时读取当前项目页面、组件和样式，展示普通更新提示、强制更新界面及手动检查入口的可见预览，列清启动/定时/手动/安装前触发点、实际显示位置、按钮/关闭行为和新业务限制范围。必须等待客户明确确认 UI；第三门禁确认不替代本次确认，等待时不写业务代码，都接入也不先实施统计。适用 UI 确认后，编码前必须先阅读目标项目及修改目录的 AGENTS.md、架构/编码约定、真实模块调用链和同类实现，明确复用组件、HTTP/配置/状态/错误/日志/异步机制及验证命令；简短报告有代码依据的落实摘要后直接编码，不新增确认门禁。保持现有架构和前端栈，Rust 实现可信服务职责，遵守目录、依赖方向、命名及测试规则，不套服务端模板或重构无关代码。UI 确认与架构核验完成后按已有授权编码和本地验收，不再问是否开始。仅统计默认无打扰，没有可见 UI 变更则记 UI 确认不适用；若改应用内隐私界面则先预览确认。复用现有风格，强更仅按有效 block_new_operations 限制新业务，保留已有任务和更新/重试/退出。完整规则见 [UI 方案与位置确认](../skills/bifang-public-services-onboarding/references/integration-contract.md#先展示并确认-ui再编码)。

在已有客户端实施授权内执行 [第四门禁完整清单](../skills/bifang-public-services-onboarding/references/integration-contract.md#第四门禁客户端本地实施与验收)，复用前三门禁事实与默认值，自动修复本轮问题及复验，不重复索取技术参数或笼统确认。

| 范围   | 实施步骤                                                                                                               | 验收条件                                                                                                                    | 单独授权操作                                                                            |
| ------ | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |

## URL 一句话如何工作

1. 先询问接入范围并等待明确选择，通过第一门禁；该门禁先于阶段 0。
2. 记录当前客户端 cwd、Task、Git 分支、HEAD 和工作区状态。
3. 对规范 GitHub URL 执行只读 `git ls-remote --symref`；在客户端之外的隔离目录获取权威仓库，不建 submodule、不复制进业务源码。
4. 核验 checkout 是 Git top-level、origin 精确匹配规范 URL、整个仓库相对 HEAD 干净、所需源文件均受 Git 管理且不含符号链接/重解析点、`.pyc` 或 `__pycache__`，并要求本地 HEAD 精确等于远端默认分支实时 advertised HEAD。
5. 保持 cwd 位于原客户端 Git 仓库内，运行权威仓库 bootstrap 并传入客户端根目录；bootstrap 扫描、核验客户端未变后安装 Skill，输出阶段 0。调用者负责确认 firstGate 已通过，脚本不代替对话确认。
6. 同轮完整读取已安装 Skill，按第二门禁完成/复用设备授权，取得并验证所选配置，再通过第三门禁方案与请求明细确认后进入第四门禁，在原授权内实施及本地验收；不重复索取技术参数，必须确认填好的请求明细，不把读取文档当实际获取配置。

Bootstrap 自身不改客户端；真正的客户端修改由安装后的 Skill 在原 cwd 中完成。权威源码与目标客户端不能重叠；目标客户端可以位于 `CODEX_HOME/worktrees/`，但不能与实际 Skill 安装目录重叠。来源不符、源码全仓不干净、HEAD 不是远端当前默认提交、同名 Skill 无法证明为当前规范版本或允许列表内精确已发布的 v1 / v2 树、基础设施来源提交不实、HEAD 低于基线、路径含符号链接/重解析点、Python bytecode/cache 或必需文件缺失时，必须停止，不能拼凑版本。bootstrap 安装路径不会执行 `CODEX_HOME`、用户目录或环境变量指定的外部 `quick_validate`。

## 只读扫描

向导先运行：

```text
python <skill-root>/scripts/scan_project.py <project-root>
```

Windows 使用：

```powershell
py -3 -X utf8 -B <skill-root>\scripts\scan_project.py <project-root>
```

扫描和人工代码审查共同确认：

- 框架、语言和正常启动入口；
- 唯一 SemVer 来源；
- 平台、架构与发布渠道；
- AppConfig、本地匿名身份和每日门禁；
- 主窗口 ready hook、安全外链与完整退出；
- 当前 APP_ID 和 telemetry 路由；
- 旧静态更新客户端、URL、14 字段 parser、rollout 与兼容开关；
- 新更新中心地址、目标平台、安装形态与客户端 Token 注入状态；
- Git 中用户已有改动。

`scan_incomplete=true` 时必须列出跳过文件，不能声称旧协议已经删除。脏工作区不等于失败，但向导不能 reset、clean、stash、切分支或覆盖用户改动。

## Profile v2

下文是联合接入 Profile 的字段和命令，按第一门禁裁剪；仅统计不得套用 `--require-update-center` 或补造更新配置。现有机器校验的单服务限制按 Skill 的 Profile 说明报告，不因模板扩大用户选择。

档案路径固定为 `.bifang/public-services-profile.json`。它保存非敏感接入事实：产品、APP_ID、框架、平台/架构、版本来源、生命周期钩子、CloudBase 公网地址、telemetry endpoint、新更新中心地址、实际更新目标、离线策略、认证状态、门禁和阶段。

关键字段：

```json
{
  "profile_schema_version": 2,
  "display_name": "毕方示例工具",
  "update_transport": "client-update-center-v1",
  "update_center_base_url": "https://update.meetelf.com",
  "update_center_auth_status": "unknown",
  "offline_enforcement": "service-default",
  "update_targets": [
    {
      "os": "windows",
      "architecture": "x86_64",
      "channel": "stable",
      "installation_type": "installed"
    }
  ],
  "legacy_update_status": "detected"
}
```

Profile 不得保存 Key、Secret、Token、Cookie、Authorization、数据库凭据、账号、硬件 ID、本机绝对路径或任何敏感值/摘要。旧 Profile v1 先只读验证与对照，再在规范一句话授权下生成确定性的 v2；无证据的字段保持未知，不能为了过校验填假值。

负责人明确要求本机联调时，`update_center_base_url` 可设为 `http://127.0.0.1:8080/`。资源派生将使用该实际地址；仅本地结果不能标记生产服务或线上客户端 E2E 已验证，也不能完成阶段 6/7。不要向本地测试服务提供生产 Token。

写后运行：

```text
python <skill-root>/scripts/validate_profile.py .bifang/public-services-profile.json --require-update-center
python <skill-root>/scripts/derive_resources.py --profile .bifang/public-services-profile.json
```

`display_name` 必须是从发布产品配置、窗口标题或负责人说明确认的中文名，1–100 个 Unicode 字符，不能包含首尾空白、控制/格式字符或标记符号 `<`、`>`。不使用英文 APP_ID、npm 包名或仓库名代替，也不凭空翻译。草稿可以暂缺名称；Profile 完成或名称交接前必须补全。资源派生结果会带上 `display_name` 和 `dashboard_app_labels`。

在已获阶段 2 授权的运营精灵任务中，只接新更新中心且没有真实旧发布流的工具，先运行 `npm run cloudbase:app:add -- <app_id>` 登记仅统计资源；已有真实旧发布流则继续保留，不能虚构 code。然后执行：

```powershell
npm run cloudbase:app:name -- <app_id> "<Profile 中确认的中文名>"
npm run cloudbase:labels:check -- --profile-file "<已校验的 Profile 交接文件路径>"
npm run cloudbase:config:check
```

名称仅维护于 `cloudbase/functions/operations-dashboard/src/app-labels.json`，`cloudbase/apps.json` 继续负责技术身份与发布流。完整名称覆盖检查通过且名称与 Profile 一致，才标记 `app_display_name_registered=true`；阶段 3 会校验这一门禁。客户端接入任务只交接映射，不因这一步自动获得运营精灵仓库的修改或部署权限。

阶段 4 的最终计划应明确列出看板同步范围并取得授权。部署后，使用已有登录会话核对完整 `appIds`、`appLabels` 和全部发布流，以及下拉框、发布流应用列和全部应用的版本画像；本工具名称精确匹配 Profile 后才标记 `dashboard_display_name_verified=true`。单纯修改本地名称表不等于线上生效；阶段 5 的客户端本地接入仍可在云端验证前完成。

## 客户端迁移

只执行第一门禁选中的服务：以下日活段落用于选择统计的任务，更新迁移/清理段落用于选择更新的任务。未选部分既有行为不变，不纳入新增接入验收。

保留正确的 `daily_active`：应用专属 AppConfig、APP_ID 隔离、联网前落盘、北京时间同日一次、失败不重试。

同时核对已有每日请求的必填 `app_version`：从真实制品的唯一版本来源取值，公共 SDK 通过 `TelemetryClient.init({appVersion, ...})` 映射上报，与更新检查的当前版本使用同一来源。`sdk_version` 固定为 `3.0.0`，服务端等值校验，不能填 Rust crate 或自选适配器版本；Profile `current_version` 只是本次实施快照。无需新增版本上报接口，也不能写死应用占位版本。

本地接入必须捕获宿主序列化请求，证明实际 `app_version` 与来源一致，并在更换测试版本和日期后随之改变；同日升级仍不能多发。通过后才标记 `telemetry_app_version_verified=true`。真实客户端阶段另行验证制品版本、服务端接受值和活跃版本画像一致，才标记 `telemetry_app_version_online_verified=true`；本地验证不能冒充此证据。

版本检查请求保持为：

```http
POST https://update.meetelf.com/api/v1/apps/{app_id}/update-checks
Authorization: Bearer <运行时客户端 Token>
Content-Type: application/json
```

请求必须携带真实版本、平台、架构、安装形态、持久随机 UUID、触发方式和实际已实现能力。仅 HTTP 201 解析响应；按照 `decision`、`enforcement` 和 `action` 决策。强更只阻止新业务，保留更新、重试、退出且不终止既有任务。下载校验长度和 SHA-256，安装前以 `pre_install` 重新检测并核对目标；详见新接入合同。

上方 HTTP 片段只定位接口，不是完整参数表。Updater 有九个必填 body 字段和可选 locale，可选 Idempotency-Key 用于同次重试；新检测不重放旧键。Windows x86 对应 Updater architecture=x86、telemetry/Profile arch=ia32；系统版本不带多余前导零，locale 按 BCP 47 校验。完整响应为 16 个顶层字段，非空 release/ artifact 分别有 5/11 个直接字段；必须按 reference 的可空、范围与组合约束验证。

telemetry 仍使用 Profile 中确认的 CloudBase 默认 origin；更新中心域名不替代统计地址。生产 DNS、TLS、应用、策略及 Token 尚未核实前不得声明线上验证通过。

看板“发布流最高版本”来自旧运营端版本发布记录 `code_version`，客户端上报的 `app_version` 用于活跃版本画像。仅统计工具没有旧发布流时如实显示“未登记旧发布流”，新更新中心的发布状态在更新后台查看。客户端接入、上报或检查更新都不自动发布版本。

必须删除：

- 旧静态更新 Base URL 与 manifest 路径；
- 14 字段 manifest parser/types；
- 本地 rollout、min-supported 与旧强制更新判定；
- 双协议、fallback、兼容开关；
- 只验证旧实现的测试、夹具和文档。

可以保留并复用：严格 SemVer、安全 URL、主窗口异步时序、UI、外链和完整退出。

客户端使用更新中心的客户端 Token，绝不使用管理凭据。Token 从运行时安全注入，原值不进 Git、Profile、源码、普通日志、命令行参数或截图。历史 application-version 服务的凭据与资源继续按原部署事实管理，不自动下线。

## 八个阶段

阶段号标识当前交付结果，不是必须顺序累积的进度条。阶段 5 只依赖本地 Profile、客户端实现与测试，可以在阶段 4 云部署前完成；阶段 6 才要求真实服务、运行凭据、构建制品和 GUI E2E。Profile 的 `legacy_client_update_removed` 只证明客户端旧代码已删，`legacy_cloud_resources_removed` 只在阶段 8 的精确线上退役完成后为真。

| 阶段 | 可验证结果                            | URL 一句话授权         |
| ---- | ------------------------------------- | ---------------------- |
| 0    | 权威来源验证与只读扫描                | 是                     |
| 1    | Profile v2                            | 是                     |
| 2    | 运营精灵登记 APP_ID、历史拓扑和中文名 | 否，运营精灵任务       |
| 3    | CloudBase 配置与只读计划              | 否                     |
| 4    | 服务部署与公网 HTTP E2E               | 否，写入前再次确认     |
| 5    | 当前客户端替换/删除旧协议与本地测试   | 是                     |
| 6    | 构建、安装、真实 GUI E2E              | 否，另有明确要求       |
| 7    | 发布与推送                            | 否，写入前再次确认     |
| 8    | 线上旧静态资源删除                    | 否，精确预检后再次确认 |

一个客户端 Task 的 URL 一句话先通过范围第一门禁，再在阶段 0+1+5 内完成所选服务的本地接入；不默认两项都接。它不横跨到另一客户端，也不把 mock、编译或 HTTP 测试冒充真实 GUI E2E。
