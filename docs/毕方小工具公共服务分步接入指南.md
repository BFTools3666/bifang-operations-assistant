# 毕方小工具公共服务分步接入指南

## 先看结论

新小工具不需要购买自有域名、HTTPS 证书或第二个 CloudBase 环境。毕方的轻量方案是：所有小工具共用负责人已有的一个免费 CloudBase 环境和平台默认 HTTPS 域名，每个小工具则使用独立的 `APP_ID`、云函数、数据集合、统计路由、本地状态目录和更新文件。

HTTPS 仍然是必须的。启动统计会传输匿名安装标识、版本、平台和架构，更新检查会读取下载地址与 SHA-256；不能用明文 HTTP 让中间人篡改。CloudBase 平台默认域名已提供 HTTPS，因此“必须 HTTPS”不等于“必须买域名或证书”。

> 费用红线：所有工具共享免费额度和故障域，并非无限容量。任何页面或命令一旦出现非零金额、套餐升级、按量计费、超限扣费、自动续费、资源包、域名或证书购买提示，立即停止并请负责人确认。不创建第二个环境，不开启超限按量或自动续费。

## 这个向导解决什么

在任意小工具项目中显式调用：

```text
$bifang-public-services-onboarding
```

向导先检查项目，再每轮只询问 1–3 个从代码与配置中无法确认的简短问题。已确认的非敏感信息保存在目标项目的 `.bifang/public-services-profile.json`，下次调用会从该档案继续，不会反复问已有答案。

向导只在用户明确选择一个实施阶段后，才能修改该阶段范围内的文件。“继续”、“按方案做”或完善档案都不等于授权部署、发布、推送、购买、删除或下线旧资源。

## 第一步：让向导自动检查

在目标小工具的仓库根目录调用 Skill。向导会先做只读检查：

- 框架与语言，例如 Electron/TypeScript、Tauri/Rust 或其他原生程序；
- 正常启动入口与当前 SemVer 的权威来源；
- 应用专属 AppConfig 目录策略；
- 主窗口显示完成位置、打开外部链接方法和完整退出程序的方法；
- 支持的平台与架构；
- 是否已有统计、更新、`APP_ID` 或历史 `/v1/track`；
- 当前 Git 分支、提交和工作区状态。

不要把搜索不到当成“不存在”。如果启动完成钩子或退出路径无法从代码确认，向导才用一个简短问题请用户指明。
协议档案中的架构值统一为 `x64 | arm64 | ia32`。项目内部使用 `amd64`、`aarch64` 或 `x86` 时，向导先依据构建配置映射到这三个公共值，无法确认才询问。

## 第二步：每次只回答少量问题

向导按当前缺失项每轮询问 1–3 个问题，不会一次抛出整张问卷。通常顺序是：

1. 中文产品名和用途或英文功能关键词。
2. 负责人和计划支持的平台。
3. 建议的唯一 `APP_ID`。
4. 使用哪一个已有 CloudBase 免费环境，以及 `APP_ID` 是否已登记。
5. 独立函数、集合、路由和更新文件是否已部署。
6. 隐私说明位置。
7. 本次仅生成方案，还是进入某一个明确阶段。

`APP_ID` 只能使用小写字母、数字和短横线，建议格式为 `bifang-<product-key>`。向导必须展示建议值和完整资源映射，等待用户确认；不得自行把建议值登记为不可随意更改的正式编号。

## 第四步：只选择一个任务阶段

每次调用最多执行用户明确选择的一个阶段：

1. **完善接入档案**：只检查并写入 `.bifang/public-services-profile.json`。
2. **在运营精灵登记新应用**：只在基础设施仓库追加已确认的 `APP_ID`，并生成默认关闭的更新文件。
3. **生成并审查 CloudBase 资源配置**：检查生成配置和 dry-run，不部署。
4. **部署独立资源并完成线上 E2E**：必须另有对该阶段的明确授权，并在新函数、新集合、新路由和新清单间完成真实验收。
5. **在业务客户端实施接入**：只修改客户端源码和本地配置，不顺带打包或发布。
6. **构建、安装和真实客户端 E2E**：使用确定的安装包和进程路径验证启动、每日一次、更新提示和退出。
7. **发布与迁移观察**：在负责人授权后发布，保留旧资源并观察新旧客户端数据。
8. **经负责人确认后清理旧资源**：有备份、观察结论和单独删除/下线授权后才可执行。

前置阶段不完整时，向导会列出“缺失门禁”，而不是把后续阶段标成已完成。

Node/Electron/TypeScript 项目进入阶段 5 时还有一个可移植分发门禁：`@bifang/telemetry-update-sdk` 目前没有发布到公网 npm，仓库也不提交 `dist`，不能假设直接 `npm install` 就能获得可用产物。实施任务必须在“固定版本 tarball、私有包、仓库内受控复制或 workspace”中明确选择一种，全部使用相对路径，并在接入档案或项目锁文件中记录 SDK 版本与产物哈希。随后运行 `verify_sdk_distribution.py`：本地 tgz/目录必须真实存在且计算 hash 一致；私有包必须使用精确版本和不可变引用，并有负责人签认的项目内 JSON 证据，输出会明确它没有验证远端包字节。不得引用开发者电脑的绝对路径或环境变量路径。

## 上线门禁

至少要逐项确认：

- `APP_ID` 已由用户确认，且在 `cloudbase/apps.json` 中唯一登记。
- 函数只允许该 `APP_ID`，`TELEMETRY_COLLECTION` 和 `TRACK_PATH` 与资源预览一致。
- 目标数据集合已人工创建且权限为 `ADMINONLY`；客户端没有数据库凭据。
- 对应平台的更新清单存在；未上线时必须 `enabled=false`、`rollout=0`，不得把 `.example.invalid` 占位地址开启为真实更新。
- telemetry 和 update check 默认关闭，只在配置完整、隐私说明到位且线上链路验收后开启。
- 客户端使用自己的 AppConfig 目录，每个 `APP_ID` 的 `install_id` 和每日标记不与其他工具共用。
- 主窗口正常显示后再低优先级检查更新；统计失败不阻塞启动，且当天不重试。
- 更新链接必须是安全的公网 HTTPS，标题和说明按不可信纯文本渲染，必需更新能走宿主完整退出路径。
- 当天首次正常启动最多产生一次 `daily_active` POST，且记录只进入该工具的集合。
- 公开隐私说明已告知匿名安装标识和服务端来源 IP 的用途、最短保留和对外遮挡要求。
- 档案中 `privacy_notice_ready` 已由负责人确认为 `true`；否则不得开启 telemetry，也不得发布含该功能的客户端。
- 已运行本地完整测试、CloudBase 配置检查和 dry-run；预览中没有删除项、陌生资源或付费提示。

## 历史 `/v1/track` 怎么迁移

搜到共享 `/v1/track`、`telemetry`、`telemetry_events` 或 `example-tool` 时，先标记为“历史链路待迁移”，不要就地改名或删除。安全次序是：

1. 保留旧函数、旧路由、旧集合、旧更新文件和历史数据。
2. 新建并验证独立 `/apps/<app_id>/v1/track` 链路。
3. 发布指向新链路的客户端，设置明确观察期。
4. 统计报表注明数据来自新集合、旧集合或两者合并，避免误读。
5. 确认没有需要旧链路的客户端后，由负责人单独授权阶段 8。

在旧客户端仍有使用者时删除旧路由会造成 404，旧数据也可能再无法核对。因此“新链路已通”不是删除旧资源的授权。

## 测试与回滚

本地验证先于线上动作：

1. 运行目标项目自带的格式、类型、单元、构建和安装验证。
2. telemetry 和 update 保持关闭，用本地 fake transport/server 验证启动时序、一天一次和失败静默。
3. 在运营精灵中运行 `npm run check`、`npm run cloudbase:config:check`，然后只做 `tcb deploy --dry-run`；若整份配置还包含其他应用变更，再运行 `npm run cloudbase:app:deploy:plan -- <app_id> --env-id <现有免费环境ID> --origin <平台默认HTTPS源>` 固化目标范围，仍不部署。
4. 只在阶段 4 已单独授权且所有门禁通过时，才做新资源的线上 E2E。
5. 安装后真实客户端 E2E 必须核对安装包、可执行文件路径、进程和窗口，不用静态检查代替真实启动。

回滚时保持范围对称：档案阶段只回滚档案；客户端阶段关闭 feature flags 并恢复上一版客户端；发布阶段先停止新版放量，旧链路和旧数据仍保留。不得把“回滚”理解为删库、删函数或下线旧路由。

`bifang-screen-recorder` 是根据用途生成的建议值，不表示它已被负责人确认、正式登记或部署。

向导还必须醒目标出以下现状与新规则的差距：

- `public-services.json` 是当前公共服务配置的事实来源；它目前使用 `APP_ID=bifang-tools`，telemetry 和 update 两个开关均为 `true`。
- `bifang-tools` 是运营精灵现有工具的编号，新规则下录屏助手不得继续复用。
- 当前仍有历史 `/v1/track` 兼容链路，不能直接覆盖或删除；必须用新 `APP_ID` 配套整组独立资源并设置迁移观察期。

- 非 Windows 的外链打开当前是 `unsupported`；在没有新平台实现和 E2E 前，支持平台只能写 Windows x64。

1. 负责人，以及是否计划扩展到 Windows x64 之外的平台。
2. 是否确认唯一 `APP_ID` 建议 `bifang-screen-recorder`。
3. 要共用的现有 CloudBase 免费环境，以及该 `APP_ID` 的登记和独立资源部署状态。
4. 现有隐私文本是否已经负责人审批为正式说明。
5. 本次是只生成方案，还是明确进入哪一个阶段。

对于目前的 `0.7.0` 客户端，接入公共服务属于新功能，可预览建议版本 `0.8.0`；这只是 SemVer 建议，必须等负责人确认，且只在客户端实施阶段修改真实版本来源。

尚未满足的门禁至少包括：新 `APP_ID` 未确认/未登记，独立函数、集合、路由和更新文件未证明已部署，免费体验域名未经正式验收，正式更新清单未完成，历史 `/v1/track` 迁移期未开始。用户确认前，向导不修改运营精灵的登记表。

### 2. 仅完善档案

用户说“本次进入阶段 1”后，向导将已确认的非敏感信息写入 `.bifang/public-services-profile.json`，运行校验，并将 `current_stage` 记为阶段 1。此时：

- 没有修改业务代码；
- 没有登记 CloudBase 资源；
- 没有网络请求；
- 没有部署、发布或费用。

下次调用 Skill 时会先恢复该档案，重新核对可能变动的版本、Git 状态和代码入口，然后只询问仍然缺失的项目。

### 3. 后续阶段

当用户明确说“进入阶段 2，在运营精灵登记已确认的 `bifang-screen-recorder`”，才能去基础设施仓库登记。阶段 3 只审查配置和 dry-run；阶段 4 需要另外、清晰的部署授权。

录屏助手已有共享 `/v1/track` 历史兼容，档案必须记录迁移门禁，不能把它当成一个假设。新链路部署、新客户端发布和观察分属不同阶段；在阶段 8 之前，旧路由与历史数据一直保留。

## 安全安装或更新 Skill

权威源码保留在运营精灵仓库的 `skills/bifang-public-services-onboarding/`。Windows 上由用户手动在仓库根目录运行：

```powershell
py -3 -X utf8 -B .\skills\bifang-public-services-onboarding\scripts\install_skill.py
```
