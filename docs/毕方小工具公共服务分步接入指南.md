# 毕方小工具公共服务 3.0 接入指南

## 先看结论

每个小工具在自己的项目中只发一句：

```text
https://gitlab.kuajingvs.com/qiuyang/bifang-operations-assistant.git 帮我接入
```

向导会验证并安装权威 Skill，读取当前项目，保留 `daily_active` 遥测，把当前客户端旧更新实现替换为客户端更新中心 POST 协议，并运行本地验证。无需先记 Skill 名称，也不需要保留两套更新协议。线上部署和其他客户端仍需各自授权。

这句话只授权当前客户端里的 Profile 和接入代码变更。CloudBase 部署/删除、打包安装、真实 GUI E2E、发布、推送、购买仍是独立动作，必须在对应门禁中执行。

## URL 一句话如何工作

1. 记录当前客户端 cwd、Task、Git 分支、HEAD 和工作区状态。
2. 对规范 GitLab URL 执行只读 `git ls-remote --symref`；在客户端之外的隔离目录获取权威仓库，不建 submodule、不复制进业务源码。
3. 核验 checkout 是 Git top-level、origin 精确匹配规范 URL、整个仓库相对 HEAD 干净、所需源文件均受 Git 管理且不含符号链接/重解析点、`.pyc` 或 `__pycache__`，并要求本地 HEAD 精确等于远端默认分支实时 advertised HEAD。
4. 保持 cwd 位于原客户端 Git 仓库内，运行权威仓库的 bootstrap 并传入该客户端根目录；bootstrap 先扫描，以客户端分支、HEAD、index、porcelain 状态和扫描范围内容摘要复核客户端未变，再安装 Skill，最后统一输出阶段 0 结果。
5. 同一轮完整读取已安装 Skill，继续写 Profile v2 和迁移客户端，不要求用户再输入 `$bifang-public-services-onboarding`。

Bootstrap 自身不改客户端；真正的客户端修改由安装后的 Skill 在原 cwd 中完成。权威源码与目标客户端不能重叠；目标客户端可以位于 `CODEX_HOME/worktrees/`，但不能与实际 Skill 安装目录重叠。来源不符、源码全仓不干净、HEAD 不是远端当前默认提交、同名 Skill 无法证明为当前规范版本或允许列表内精确已发布的 v1 / v2 树、基础设施来源提交不实、HEAD 低于基线、路径含符号链接/重解析点、Python bytecode/cache 或必需文件缺失时，必须停止，不能拼凑版本。bootstrap 安装路径不会执行 `CODEX_HOME`、用户目录或环境变量指定的外部 `quick_validate`。

## 只读扫描

向导先运行：

```text
python <skill-root>/scripts/scan_project.py <project-root>
```

Windows 使用：

```powershell
py -3 -X utf8 -B <skill-root>\scripts\scan_project.py <project-root>
```

扫描和人工代码审查共同确认：

- 框架、语言和正常启动入口；
- 唯一 SemVer 来源；
- 平台、架构与发布渠道；
- AppConfig、本地匿名身份和每日门禁；
- 主窗口 ready hook、安全外链与完整退出；
- 当前 APP_ID 和 telemetry 路由；
- 旧静态更新客户端、URL、14 字段 parser、rollout 与兼容开关；
- 新更新中心地址、目标平台、安装形态与客户端 Token 注入状态；
- Git 中用户已有改动。

`scan_incomplete=true` 时必须列出跳过文件，不能声称旧协议已经删除。脏工作区不等于失败，但向导不能 reset、clean、stash、切分支或覆盖用户改动。

## Profile v2

档案路径固定为 `.bifang/public-services-profile.json`。它保存非敏感接入事实：产品、APP_ID、框架、平台/架构、版本来源、生命周期钩子、CloudBase 公网地址、telemetry endpoint、新更新中心地址、实际更新目标、离线策略、认证状态、门禁和阶段。

关键字段：

```json
{
  "profile_schema_version": 2,
  "display_name": "毕方示例工具",
  "update_transport": "client-update-center-v1",
  "update_center_base_url": "https://update.meetelf.com",
  "update_center_auth_status": "unknown",
  "offline_enforcement": "service-default",
  "update_targets": [
    {
      "os": "windows",
      "architecture": "x86_64",
      "channel": "stable",
      "installation_type": "installed"
    }
  ],
  "legacy_update_status": "detected"
}
```

Profile 不得保存 Key、Secret、Token、Cookie、Authorization、数据库凭据、账号、硬件 ID、本机绝对路径或任何敏感值/摘要。旧 Profile v1 先只读验证与对照，再在规范一句话授权下生成确定性的 v2；无证据的字段保持未知，不能为了过校验填假值。

写后运行：

```text
python <skill-root>/scripts/validate_profile.py .bifang/public-services-profile.json --require-update-center
python <skill-root>/scripts/derive_resources.py --profile .bifang/public-services-profile.json
```

`display_name` 必须是从发布产品配置、窗口标题或负责人说明确认的中文名，1–100 个 Unicode 字符，不能包含首尾空白、控制/格式字符或标记符号 `<`、`>`。不使用英文 APP_ID、npm 包名或仓库名代替，也不凭空翻译。草稿可以暂缺名称；Profile 完成或名称交接前必须补全。资源派生结果会带上 `display_name` 和 `dashboard_app_labels`。

在已获阶段 2 授权的运营精灵任务中，只接新更新中心且没有真实旧发布流的工具，先运行 `npm run cloudbase:app:add -- <app_id>` 登记仅统计资源；已有真实旧发布流则继续保留，不能虚构 code。然后执行：

```powershell
npm run cloudbase:app:name -- <app_id> "<Profile 中确认的中文名>"
npm run cloudbase:labels:check -- --profile-file "<已校验的 Profile 交接文件路径>"
npm run cloudbase:config:check
```

名称仅维护于 `cloudbase/functions/operations-dashboard/src/app-labels.json`，`cloudbase/apps.json` 继续负责技术身份与发布流。完整名称覆盖检查通过且名称与 Profile 一致，才标记 `app_display_name_registered=true`；阶段 3 会校验这一门禁。客户端接入任务只交接映射，不因这一步自动获得运营精灵仓库的修改或部署权限。

阶段 4 的最终计划应明确列出看板同步范围并取得授权。部署后，使用已有登录会话核对完整 `appIds`、`appLabels` 和全部发布流，以及下拉框、发布流应用列和全部应用的版本画像；本工具名称精确匹配 Profile 后才标记 `dashboard_display_name_verified=true`。单纯修改本地名称表不等于线上生效；阶段 5 的客户端本地接入仍可在云端验证前完成。

| -------------- | --------------------------------------------------- |
| Telemetry 函数 | `telemetry-bifang-screen-recorder`                  |
| Telemetry 路由 | `/apps/bifang-screen-recorder/v1/track`             |
| Telemetry 集合 | `telemetry_bifang_screen_recorder`                  |

## 客户端迁移

保留正确的 `daily_active`：应用专属 AppConfig、APP_ID 隔离、联网前落盘、北京时间同日一次、失败不重试。

同时核对已有每日请求的必填 `app_version`：从真实制品的唯一版本来源取值，公共 SDK 通过 `TelemetryClient.init({appVersion, ...})` 映射上报，与更新检查的当前版本使用同一来源。`sdk_version` 表示 SDK 版本，Profile `current_version` 只是本次实施快照。无需新增版本上报接口，也不能写死占位版本。

本地接入必须捕获宿主序列化请求，证明实际 `app_version` 与来源一致，并在更换测试版本和日期后随之改变；同日升级仍不能多发。通过后才标记 `telemetry_app_version_verified=true`。真实客户端阶段另行验证制品版本、服务端接受值和活跃版本画像一致，才标记 `telemetry_app_version_online_verified=true`；本地验证不能冒充此证据。

版本检查请求保持为：

```http
POST https://update.meetelf.com/api/v1/apps/{app_id}/update-checks
Authorization: Bearer <运行时客户端 Token>
Content-Type: application/json
```

请求必须携带真实版本、平台、架构、安装形态、持久随机 UUID、触发方式和实际已实现能力。仅 HTTP 201 解析响应；按照 `decision`、`enforcement` 和 `action` 决策。强更只阻止新业务，保留更新、重试、退出且不终止既有任务。下载校验长度和 SHA-256，安装前以 `pre_install` 重新检测并核对目标；详见新接入合同。

telemetry 仍使用 Profile 中确认的 CloudBase 默认 origin；更新中心域名不替代统计地址。生产 DNS、TLS、应用、策略及 Token 尚未核实前不得声明线上验证通过。

看板“发布流最高版本”来自旧运营端版本发布记录 `code_version`，客户端上报的 `app_version` 用于活跃版本画像。仅统计工具没有旧发布流时如实显示“未登记旧发布流”，新更新中心的发布状态在更新后台查看。客户端接入、上报或检查更新都不自动发布版本。

必须删除：

- 旧静态更新 Base URL 与 manifest 路径；
- 14 字段 manifest parser/types；
- 本地 rollout、min-supported 与旧强制更新判定；
- 双协议、fallback、兼容开关；
- 只验证旧实现的测试、夹具和文档。

可以保留并复用：严格 SemVer、安全 URL、主窗口异步时序、UI、外链和完整退出。

客户端使用更新中心的客户端 Token，绝不使用管理凭据。Token 从运行时安全注入，原值不进 Git、Profile、源码、普通日志、命令行参数或截图。历史 application-version 服务的凭据与资源继续按原部署事实管理，不自动下线。

## 八个阶段

阶段号标识当前交付结果，不是必须顺序累积的进度条。阶段 5 只依赖本地 Profile、客户端实现与测试，可以在阶段 4 云部署前完成；阶段 6 才要求真实服务、运行凭据、构建制品和 GUI E2E。Profile 的 `legacy_client_update_removed` 只证明客户端旧代码已删，`legacy_cloud_resources_removed` 只在阶段 8 的精确线上退役完成后为真。

| 阶段 | 可验证结果                            | URL 一句话授权         |
| ---- | ------------------------------------- | ---------------------- |
| 0    | 权威来源验证与只读扫描                | 是                     |
| 1    | Profile v2                            | 是                     |
| 2    | 运营精灵登记 APP_ID、历史拓扑和中文名 | 否，运营精灵任务       |
| 3    | CloudBase 配置与只读计划              | 否                     |
| 4    | 服务部署与公网 HTTP E2E               | 否，写入前再次确认     |
| 5    | 当前客户端替换/删除旧协议与本地测试   | 是                     |
| 6    | 构建、安装、真实 GUI E2E              | 否，另有明确要求       |
| 7    | 发布与推送                            | 否，写入前再次确认     |
| 8    | 线上旧静态资源删除                    | 否，精确预检后再次确认 |

一个客户端 Task 的 URL 一句话是阶段 0+1+5 的单一“完成客户端接入”结果。它不横跨到另一个客户端，也不把 mock、编译或 HTTP 测试冒充真实 GUI E2E。

## 两个实际客户端

### 鼠标精灵

- APP_ID：`bifang-mouse-clicker`
- 平台流：Windows x64 stable
- 历史 application-version code：`bifang-mouse-clicker`，不放入新更新请求。
- 接入 Task 必须以用户明确确认的当前 working tree 为权威；不能 `reset`、`stash`、`clean`，也不能从旧 HEAD 另起导致改动丢失。实际版本和工作树状态在任务开始时实时核对，本指南不冻结一次性快照。
- 最终使用新构建的准确 Windows EXE/安装包验证更新状态、错误状态、完整退出和不再请求旧协议。

### 录屏助手

- APP_ID：`bifang-screen-recorder`
- 历史 Windows code：`bifang-screen-recorder-windows-x64`；历史 macOS code：`bifang-screen-recorder-macos-arm64`。它们不放入新更新请求。
- 新请求必须填写实际运行程序的平台、架构、安装形态与通道，不能运行时猜平台。
- 本机只可形成 Windows 真实 E2E；macOS 必须在真实 Mac 上保持独立 `Unverified`，直到取得原生证据。

两个项目都没有广告 UI 时，不为凑接口新增广告功能；历史广告与管理端点仍由旧服务自己的契约 E2E 覆盖。

## 云端与费用门禁

只复用负责人确认的现有免费 CloudBase 环境和平台默认 HTTPS 域名。不创建第二环境，不购买域名、证书、套餐或资源包，不开启按量超限、超限扣费或自动续费。

阶段 4 和 8 前必须重新只读枚举远端函数、路由、集合、权限、索引、hosting 文件、默认域名和费用状态，展示精确创建/更新/删除目标与回滚方式，再等待负责人明确“继续”。任何非零金额或升级提示立即停止。

## 安装与验证 Skill

从经过验证的权威仓库运行：

```powershell
py -3 -X utf8 -B skills\bifang-public-services-onboarding\scripts\install_skill.py
```

Installer 会校验 Skill 结构、2.1.0/3.0/1.0 版本、来源提交、规范 GitLab URL 和隐式触发策略；拒绝 `.pyc` / `__pycache__`、来源不明的同名 Skill、版本降级或同版本不同内容；只为允许列表内精确匹配权威已发布树的旧 Skill 开放迁移，包括 v1 / infrastructure 2.1 和已发布的 v2.0.0，通过暂存和可回滚替换原子升级，不改其他 Skill。bootstrap 会显式禁用安装器的外部 `quick_validate` 搜索，避免执行未由本次权威 checkout 证明的脚本。

## 报告证据

每轮交付都要列出实际修改、删除的旧协议文件/符号、Profile 与资源派生、测试命令和结果，以及明确未执行的部署、安装、GUI、发布、推送、购买或线上删除。真实 E2E 证据必须绑定准确制品 SHA、进程/窗口、最终请求 URL 和遮挡凭据后的结果。
