# 应用版本 API 零代码接入契约、实施状态与可行性报告

## 结论

**可行，运行时零代码接入的可行性高；运营精灵服务端已完成本地实现和本地 HTTP E2E。**目标不是让对方修改接口，也不是让毕方客户端兼容旧协议，而是让毕方运营精灵在外部表现上实现对方软件已经使用的契约：现有程序二进制保持不变，只修改服务地址、TLS/证书信任和 `x-app-key`、`x-app-secret` 配置，就能把请求切到毕方服务。

本文件冻结的是**已经在仓库中实现的目标契约**，但不是已部署或原程序已验收的事实。实现位于 `cloudbase/functions/application-version-api/`，部署模板与服务级只读计划也已生成；当前线上资源、静态 `/updates/<app_id>/<platform>.json` 更新链路、SDK、鼠标精灵和录屏助手均未修改。由于旧毕方客户端尚未公开发布，后续直接演进到这一套契约，不建设长期双协议兼容层；遥测协议不在本次替换范围内。

机器可执行定义见 [`../contracts/application-version-api-v1`](../contracts/application-version-api-v1)。参考源是《应用版本API》v1 的本地审阅快照，文件 SHA-256 为 `6721cd6fe03db65847b7d64d8bd65c102c67b0a3563ef8803475a3ce5ebda8c7`。参考文档中出现过凭据示例，本仓库不复制、不接受也不验证该值。

## “零代码接入”的验收定义

只有同时满足以下条件，才能声称无缝接入：

1. 对方小工具的可执行文件字节和 SHA-256 保持不变，没有重新编译或补丁。
2. 只修改它原本允许修改的服务主机或 Base URL、TLS/证书信任、App Key 和 App Secret。
3. 最终请求到达毕方域名，路径、方法、两个请求头和 JSON 形状均无需客户端适配。
4. 无更新、提示更新、强制更新、停止更新、空广告和有广告场景均由原程序正确处理。
5. 不依赖 HTTP 重定向、客户端注入、代理改写响应或手工替换程序文件来伪装兼容。

仅用 `curl` 或单元测试请求成功，只能证明服务端契约成立，不能证明原程序零代码兼容。最终验收必须包含一次真实原程序请求观测。

## 外部契约范围

### 运行时冻结面

现有小工具正常运行只需要两个读取接口。这两个接口是零代码目标的 P0：

| 方法  | Path                         | 用途                               | 冻结状态                                   |
| ----- | ---------------------------- | ---------------------------------- | ------------------------------------------ |
| `GET` | `/versions/{code}/{version}` | 根据软件编码与当前版本返回更新决策 | 本地已实现；待测试域名原程序 E2E           |
| `GET` | `/app/{code}/ads/show`       | 返回该软件要展示的广告数组         | 本地已实现；待原程序确认空数组和字段容忍度 |

运行时响应不新增 `platform`、`arch`、`sha256`、`targetVersion` 或毕方内部字段，因为现有程序没有代码去读取新字段。安全性和平台分流放在毕方内部模型与 `code`/主机映射中完成。

### 管理端暂定面

为覆盖参考文档的完整功能，OpenAPI 同时收录以下八个管理接口：

| 方法     | Path                   | 用途         |
| -------- | ---------------------- | ------------ |
| `POST`   | `/versions`            | 新增版本记录 |
| `PUT`    | `/versions/{id}`       | 编辑版本记录 |
| `GET`    | `/versions`            | 版本列表     |
| `POST`   | `/app/{code}/ads`      | 新增广告     |
| `PUT`    | `/app/{code}/ads/{id}` | 编辑广告     |
| `DELETE` | `/app/{code}/ads/{id}` | 删除广告     |
| `GET`    | `/app/ads/{id}`        | 广告详情     |
| `GET`    | `/app/{code}/ads`      | 广告列表     |

这些接口可按文档实现，但**暂不能承诺某个既有管理客户端也能零代码切换**。参考文档没有定义 POST/PUT/DELETE 的成功响应体，版本列表中的 `updateCriteria` 同时出现字符串和对象两种形状，分页示例多出且算错 `total_page`，广告列表示例也不是合法的通用分页结果。若还要替换对方的管理端，必须先观测该管理端或原服务的真实响应，再把暂定形状升级为冻结形状。

## Base URL、路径和请求头

规范 Base URL 冻结为：

```text
https://<host>/tools/version-control/v1
```

接口 Path 直接拼在其后，例如：

```text
GET https://<host>/tools/version-control/v1/versions/example-tool/1.2.0
```

`v1` 就是 API 版本，只出现这一次。不得额外拼第二个 `/v1`，服务端也不提供 `/v1/v1` 别名；该错误路径固定返回 404。

所有十个接口都接受参考文档的两个原名请求头：

```text
x-app-key: <configured key>
x-app-secret: <configured secret>
```

HTTP 头名称不区分大小写，但 OpenAPI 保留上述拼写。两个头必须同时出现；不改成 `Authorization`，也不要求现有程序增加时间戳、nonce 或签名字段。

毕方内部必须把凭据分权：

- 运行时凭据只配置 `versions:check`、`ads:show`，仅允许调用更新判定和广告展示两个 GET，并绑定允许访问的 `code`；管理列表/详情使用不同的 `versions:read`、`ads:read` 权限。即使桌面程序中的值被提取，也不能新增版本、删除广告、读取管理列表/详情或跨应用访问。
- 管理凭据仍使用相同的两个头名，但具有单独的密钥和值域，可获得管理权限。
- Secret 只保存不可逆校验值，不进入 Git、响应、普通日志或运营看板；支持短期双值轮换。
- Key 与 Secret 原值必须由密码学安全随机源生成，不能复用参考文档中的示例或人工短口令。

这种分权不要求客户端改代码，只是给不同软件配置不同的一对值。

## 版本字段与比较规则

外部版本号按参考文档接受数字点分格式：

```regex
^[0-9]+(?:\.[0-9]+)*$
```

因此 `1`、`1.2`、`1.2.3.4` 和带前导零的数字段都能被解析；不接受 `v1.2.0`、预发布标签或构建元数据。比较时：

1. 每段按任意精度非负整数比较，不按字符串比较。
2. 缺失的尾段视为 `0`，所以 `1`、`1.0`、`1.0.0` 相等。
3. 前导零不改变数值，所以 `01.002` 与 `1.2.0` 相等。
4. 永远不向更低或相同的 `codeVersion` 更新。

如果版本记录没有 `updateCriteria` 和 `versionCriteria`，默认条件是：

```text
currentVersion < codeVersion
```

两个条件字段必须同时存在或同时缺失。存在时，当前客户端版本永远是左操作数：

| `updateCriteria` | 条件                                |
| ---------------- | ----------------------------------- |
| `lt`             | `currentVersion < versionCriteria`  |
| `le`             | `currentVersion <= versionCriteria` |
| `gt`             | `currentVersion > versionCriteria`  |
| `ge`             | `currentVersion >= versionCriteria` |

更新候选仍必须同时满足 `currentVersion < codeVersion`，避免条件配置导致降级。一个 `code` 存在多条记录时，先选择数字点分比较意义下最高的 `codeVersion`，再评估该记录；相同 `code + codeVersion` 不允许重复。

数据库内部为每个已验证版本生成仅含数字的排序键，并使用 `code + version_sort_key(desc)` 组合索引一次读取最高版本；排序键不进入外部响应。这样不依赖 JavaScript 安全整数，也避免在并发写入期间通过多页扫描漏选或重复版本。

## 三个状态布尔值的真值表

写入时只允许四种组合，两个或三个 `true` 一律返回验证错误：

| 状态     | `forcedUpdate` | `promptUpdate` | `stopUpdate` | 满足版本条件时的 `update` |
| -------- | -------------: | -------------: | -----------: | ------------------------: |
| 普通更新 |        `false` |        `false` |      `false` |                    `true` |
| 强制更新 |         `true` |        `false` |      `false` |                    `true` |
| 提示更新 |        `false` |         `true` |      `false` |                    `true` |
| 暂停更新 |        `false` |        `false` |       `true` |                   `false` |

当版本条件不满足时，`update=false`，并把响应中的 `forcedUpdate`、`promptUpdate` 都归零；`stopUpdate` 保留记录值。这样即使客户端错误地单独读取强制或提示标志，也不会在没有更新时弹窗。`stopUpdate` 仅表示暂停分发更新，不解释为禁止启动软件。

## 运行时精确响应

### 更新检查

成功响应固定只包含七个字段，不夹带内部信息：

```json
{
  "update": true,
  "downloadUrl": "https://downloads.example.com/example-tool/2.0.0.exe",
  "promptContent": "发现新版本",
  "forcedUpdate": false,
  "promptUpdate": true,
  "stopUpdate": false,
  "updateContent": "<div>本次更新内容</div>"
}
```

`updateContent` 为兼容既有客户端保留字符串/受限富文本形状。写入时服务端必须做允许列表消毒，禁止脚本、事件处理器、危险 URL、外部资源自动加载和本地桥调用；从数据库读取时再次执行完整验证，任何被控制台导入、迁移或损坏的异常记录都返回通用 500，不把未验证内容下发。服务端不能假设客户端会安全处理 HTML。`promptContent`、名称和标题按普通文本保存，并拒绝 `<`、`>`，避免旧客户端错误地用 `innerHTML` 渲染时形成标记注入。

下载与广告地址只允许无凭据 HTTPS，并在不做网络请求的前提下拒绝显式本地、单标签和已知特殊用途域名/IP。该检查不能证明任意域名当前解析到公网，也不能阻止未来 DNS 重绑定；正式发布数据仍须在测试域名验收时按实际下载与广告主机建立运营白名单。

已存在应用但当前无需更新时仍返回 200 和同一七字段对象，其中 `update=false`。未知 `code` 返回 404 通用错误结构，不伪造空版本记录。

### 广告展示

成功响应固定为裸数组；没有广告时返回 `[]`：

```json
[
  {
    "id": "2001178408904765442",
    "url": "https://www.example.com/campaign",
    "image": "https://cdn.example.com/campaign.png",
    "content": ""
  }
]
```

数组项固定为 `id`、`url`、`image`、`content` 四个字段。运营端提交的链接、图片和富文本必须在服务端校验与消毒；运行时凭据不能读取其他 `code` 的广告。

## 错误与限流

错误响应沿用参考文档的包装，不把内部异常或凭据回显给客户端：

```json
{
  "model": "errors",
  "errors": {
    "model": "data.set",
    "datas": [
      {
        "model": "error",
        "code": "auth.invalid",
        "message": "请求未通过验证"
      }
    ]
  }
}
```

HTTP 状态冻结为 400（格式/字段）、401（缺少或错误凭据）、403（权限或跨 `code`）、404（资源不存在）、409（重复/并发冲突）、429（限流）、500（通用内部错误）。每个接口名义限制为 10 QPS；实施时按凭据并叠加来源 IP 防护，429 返回 `Retry-After`。限流维度不改变客户端请求形状。

## 平台与制品分流

参考契约没有 `platform` 或 `arch`，不能擅自在运行时请求中新增字段。毕方内部把外部 `code` 映射到唯一的 `(app_id, platform, arch, channel)` 发布流：

- 若不同平台构建可以配置不同 `code`，每个平台使用不同外部别名。
- 若它们只能配置不同主机，可用主机到发布流的服务端映射，Path 仍不变。
- 若同一个 `code`、同一个主机且请求中没有任何平台信号，服务端无法可靠区分 Windows 与 macOS；这不是后端猜测能够解决的问题，必须在真实请求观测中确认程序是否另带平台信息。

不得依赖 User-Agent 猜测平台来发布强制更新。录屏助手当前有 Windows 与 macOS 登记，因此这是它进入后续升级任务前的 P0 门禁；鼠标精灵只有 Windows，不受该歧义影响。

## 测试域名上的原程序 E2E 门禁

本地实现通过后、声明“无缝”之前，用未修改的原程序、测试只读凭据和测试域名完成一次最小观测，只记录协议元数据并遮挡凭据值：

1. 确认配置项替换的是主机、origin 还是完整 Base URL，并确认最终请求严格命中单一版本段 `/tools/version-control/v1/...`。
2. 确认两个请求头是否每次都发送，`code`/`version` 的大小写与 URL 编码方式。
3. 确认客户端是否跟随 30x、是否要求固定证书链/证书钉扎、超时和 TLS 版本。
4. 对更新接口依次返回：无需更新、提示更新、强制更新、暂停更新和错误包装，观察原 UI 行为。
5. 对广告接口依次返回 `[]` 和一个合法项目，确认它是否拒绝额外字段或空字符串。
6. 若还要接对方管理端，另外观测列表、分页、`updateCriteria` 形状及三个写接口的成功 body；否则不把管理端纳入零代码承诺。

若观测发现字段或行为差异，只调整毕方的凭据映射或响应适配器；不要求对方修改小工具程序，也不增加双 `v1` 路径。观测证据应记录原二进制 SHA-256、配置前后差异、最终请求 URL、响应样例、进程/窗口和结果截图，不记录 Secret。

## 可行性与复杂度分级

| 范围                       | 可行性                     | 主要复杂度                                   | 建议                                         |
| -------------------------- | -------------------------- | -------------------------------------------- | -------------------------------------------- |
| 原小工具版本检查零代码切换 | 高，待一次真实请求确认     | Base URL 拼接、七字段响应、状态真值表        | 第一优先实现和验收                           |
| 原小工具广告展示零代码切换 | 高，前提是它确实调用该端点 | 裸数组、内容消毒、链接安全                   | 与版本检查同一兼容层实现，可独立关闭广告数据 |
| 对方管理端也零代码切换     | 中，PDF 不足以证明         | 分页、条件字段形状、写接口成功体             | 未观测真实管理请求前不作承诺                 |
| 鼠标精灵迁移到新契约       | 高                         | 当前静态清单调用改为新 GET、真实 Windows E2E | 服务端稳定后单独做第二阶段任务               |
| 录屏助手迁移到新契约       | 高但有一个 P0 门禁         | Windows/macOS 在无平台字段时的发布流区分     | 先确认不同构建能否配置不同 `code` 或主机     |

因此，技术难点主要在毕方服务端的契约适配、权限和数据模型，不在对方小工具。只要真实请求证明配置项确实覆盖最终 Base URL/TLS/凭据，运行时无需对方配合改一组接口。

## 零代码方式无法替客户端补上的能力

这不妨碍接入，但需要把安全上限说清楚：

- 响应里不能擅自增加 `sha256`、签名或目标平台并指望旧程序使用；它没有相应代码。毕方仍应只发布签名制品、使用受控 HTTPS 下载域名，但旧程序是否验证制品只能以真实行为为准。
- 请求里没有平台/架构时，后端不能凭空可靠识别；只能使用原程序已经发送或允许配置的 `code`、主机等信息分流。
- 如果原程序把 `updateContent` 当 HTML 渲染，后端只能严格消毒内容，不能修改它的渲染器。
- 如果原程序存在且不可配置的证书或公钥钉扎，仅换域名和普通证书不会成功；必须先通过观测确认该限制不存在或确实可配置。

这些是“保持原程序不变”的自然边界，不代表需要对方重写一组 API。能够由服务端解决的差异全部留在毕方的网关、鉴权和响应适配层。

## 实施建议

建议按四个独立、可验收任务推进：

1. **契约冻结（已完成）**：OpenAPI、JSON Schema、比较/状态测试向量和真实观测清单。
2. **运营精灵服务端实现（本地已完成）**：一个共享 Event 函数承载固定契约入口，鉴权后按 `app_id` 分流到独立 versions、ads、audit 集合；管理/运行凭据分权，写操作与审计在同一事务内完成。部署计划仍保持只读。
3. **未修改原程序的测试域名 E2E（下一步）**：先展示现有免费环境、默认 HTTPS 域名、函数、路由、集合、索引、凭据映射和费用预检，再等待明确“继续”后部署并验证。若出现费用、域名或证书购买提示立即停止。
4. **鼠标精灵、录屏助手升级**：在各自本地项目中分别调用接入 Skill，改用已验收的新契约并做真实安装包 E2E。它们是第二阶段，不从本仓库主动扫描或修改。

由于旧毕方客户端未公开，第四步完成后直接移除旧更新实现和过渡开关即可；无需长期维护 `/updates` 与新 API 两套出口。移除仍属于后续明确授权的客户端/服务端变更，不在本次契约冻结内。

## 当前边界与完成标准

当前已完成目标契约、服务端源码、CloudBase 模板、服务级部署预览、函数/数据库适配器测试和真实 localhost HTTP 请求测试。localhost 结果只证明服务端边界成立，不等同于 CloudBase 或原程序 E2E。当前未执行：

- CloudBase 登录、集合/索引创建、函数/路由部署或线上验证；
- 域名、证书、套餐或资源购买；
- 云端版本/广告/审计数据库创建或测试数据写入；
- 鼠标精灵、录屏助手或第三方程序修改；
- 更新启用、发布、推送、删除或旧资源下线。

为避免形成两份互相冲突的现行协议，本轮同步维护 README、长期协议说明、机器契约、应用登记派生资源、CloudBase 生成器和测试。当前 SDK 与宿主示例仍维持旧静态更新协议，等鼠标精灵和录屏助手各自进入第二阶段任务时直接迁移，不在服务端任务中主动修改。

只有运行时两个接口在测试域名上通过真实未修改原程序 E2E 后，才能把状态从“本地已实现”提升为“零代码已验证”。当前桌面范围内只发现了参考 PDF，没有找到原程序 EXE 或配置目录；开始该 E2E 前仍需负责人提供其准确路径、实际 `code`、当前版本和可修改配置位置。
