# 接入契约与 Profile v2

整理 Skill 规范或实施所选服务时读取。第一门禁确认仅更新/仅统计/都接入；第二门禁到授权中心取得真实配置；第三门禁核验方案并向客户展示完整请求明细、等待明确确认；第四门禁完成原授权内的本地实施与验收。业务字段见下文日活合同与 [Updater 合同](client-update-center.md)。整理规范不触发真实授权或业务接入。

## 门禁顺序与放行总表

唯一顺序为：**第一门禁范围确认 → 第二门禁授权与配置验证 → 第三门禁请求明细确认 → 第四门禁 4A UI 确认 → 4B 架构与规范核验 → 4C 编码 → 4D 本地验收**。4A～4D 是第四门禁的内部检查点，不新增第五门禁。本地通过后按 [线上配置与 EXE 测试](#本地通过后更新中心配置与-exe-真实测试) 继续独立放行流程。每一步必须检查前序通过证据后才能开始；预选、未回答、过期证据、草稿、脚本成功和客户笼统说“继续”都不能补齐缺失证据。维护规范本身不触发客户接入门禁。

| 门禁/检查点    | 进入条件                         | 必须取得并返回的信息/证据                                                                                                                         | 通过条件与下一步                                                                                                       |
| -------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 1 范围确认     | 收到当前客户端接入请求           | 明确问仅更新、仅统计或都接入，记录客户选择与回复依据                                                                                              | 客户明确选择后才进入 2；未选不能验证来源、安装 Skill、扫描项目或收集参数                                               |

### 范围、阻断与证据复用

- **仅更新**：只按更新项过每个门禁，必须经过更新 UI 确认；统计记不在本次范围并保持原状。**仅统计**：只按统计项过门禁，UI 仅在没有可见变更时可记不适用，架构、编码和验收都不能省略。**都接入**：每个门禁必须两项全部达到条件；成功分支只保留当前门禁证据，失败分支在当前门禁修复，禁止单分支先进入下一门禁。客户只确认其中一项不算联合通过；需要改为单服务时由客户明确修改范围，回到第一门禁记录新范围并重新核验下游适用性，不能暗中缩减范围。
- 未通过当前门禁时，只做当前门禁范围内的核实、修正和必要澄清，不能以“并行准备”为由先执行下一门禁的正式设计、确认或实现。第一门禁后的只读扫描可以包含后续所需事实，但不提前宣称后续门禁通过。
- 每次准备转入下一门禁时，在脱敏交接记录中写明本次范围、当前门禁/检查点、证据位置、客户回复依据（仅人工确认项）、状态、缺项及允许的下一步。状态限定为未开始、进行中、待客户确认、阻断、已通过；未选服务记不在范围，合法 UI 豁免记不适用及理由。进入下一步前先复核前序状态和证据。此为交接约定，不增造配置接口字段或 Profile schema 字段。
- 复用同一项目、范围、方案、目标和有效配置下的既有证据与明确确认，不重复问；恢复会话先读取交接记录及实际项目事实，从最早未通过的门禁继续，不能从“已到阶段 5”推定前序完成。无证据或证据失效视为尚未通过，不用填写 true 补齐。
- 范围变化回到 1；权限/配置失效回到 2 核验或刷新；实际端点、身份、参数/能力实质变化重新核验 2/3 及受影响后序；UI 实质变化回到 4A；模块边界或规范变化回到 4B；本地失败回到 4C 修复后重验 4D。仅重新确认发生实质变化的项；按合同刷新同用途凭据、生成时间/随机 ID 不触发无关重复确认。回退不自动撤销/删除已写代码或清理用户工作区。
- 已知尚未部署/发布且端点、合同和身份已核验的事项可单列线上依赖；未知真实地址、必填映射或权限是当前阻断，不能用“线上待办”掩盖。单元测试用假凭据不等于第二门禁允许假配置。真实业务请求、部署、构建安装、发布、推送和删除继续遵守独立授权，第四门禁通过不自动放行这些操作。

机器入口中的门禁链是对 Skill 执行行为的声明与契约，不是已实现的运行时拦截器。bootstrap/Profile 校验通过不能代替上述证据、客户确认或门禁状态；任何旧的运维阶段编号都不能绕过本表。

## 第二门禁：授权中心授权与配置获取

第一门禁明确范围后，验证来源、只读识别当前项目，随后执行授权中心设备授权并读取所选配置。客户只需在服务端授权页完成必要的登录、改密/风险确认和批准；不再请客户逐项确认或手填一整张技术参数表。已批准、仍有效且所选服务权限足够的授权可直接复用，不能每次重新要求登录批准。

处理顺序固定为：项目取证与应用默认值 → 取得/复用授权 → 读取所选配置 → 校验字段、用途及下游端点 → 合并项目事实 → 第三门禁核验方案、展示请求明细并等待客户确认 → 第四门禁在原授权内实施并本地验收所选服务。没有成功取得有效配置，不能靠占位值、旧硬编码或假 Token 宣称门禁通过。

配置接口已定义，不再整体标为“合同待补”。真实生产授权中心地址/客户端登记、实际配置是否存在、Endpoint 与下游路由语义仍须根据部署事实核验。能从可信部署资料、响应或代码确定的内容自动取得；真正无法确定的阻断项向运维核实，不把整份配置表交给客户填写。

后续步骤：读取配置并核对环境/路由 → 第三门禁统计方案核验 → 安全分离运维密钥与客户端日活所需地址 → Rust 十字段上报/身份/每日门禁 → 本地同日/并发/失败/升级验证 → 另获对应授权后真实落库/看板验证。不给 Updater 配置接口发请求，不改或删除更新功能。取得 CloudBase 密钥不自动授权部署、购买、删除。

### 更新和统计都接入

同一实际获授两个配置 scope 的有效 OAuth access_token 可顺序读取两个独立 GET 接口；只授权一次，不收集两套账号或让用户重复批准。两个响应独立校验，不虚构一个合并配置接口或 data 包装。

| 联合事实   | 自动处理规则                                                                                                                                                                |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 项目与应用 | project_id 默认 bifang_tools；业务 APP_ID 从产品登记取证。共用新 APP_ID 时取交集 `^[a-z][a-z0-9-]{1,48}[a-z0-9]$`；既有 ID 不同不得自动改名/合并                            |
| 版本/平台  | 共用实际运行版本来源；telemetry x64→Updater x86_64，Windows ia32→x86，arm64→arm64；Linux 从系统识别 Ubuntu/Debian                                                           |
| 身份       | 复用既有稳定身份；新方案可共用随机 UUID v4，但保持两个请求字段名和应用隔离                                                                                                  |
| 凭据       | OAuth access_token 仅查配置；ClientToken 仅检查更新；SecretId/SecretKey 仅用于已授权运维，不交叉发送                                                                        |

### 门禁结果与必要交互

门禁通过依据是实际授权和所选接口成功响应、字段/下游用途验证以及可确定的项目事实，不是客户口头说“配置没问题”。非敏感记录只保留所选范围、project_id、来源与默认值依据、读取状态、错误码/请求 ID、待办；不保存完整响应、密钥、OAuth 令牌、原始安装 ID 或账号标识。

真实配置获取是本门禁明确的只读授权流程，不因此访问下游服务写测试数据、构建安装、部署、发布或删除。当前任务若仅整理规范，不执行 OAuth 或配置请求。现有联合 Profile 的单服务校验限制继续如实记录，不填假参数、不扩大范围，也不擅自添加未定义字段。

## 第三门禁：客户端接入方案与请求明细确认

第二门禁取得并验证所选配置后，第三门禁把已知事实落实到当前客户端的 Rust 接入位置、运行行为、迁移范围和验收计划。Skill 先自动完成技术核验并填好接入确认单，再在回复正文中完整展示所选服务的真实请求地址和参数，等待客户明确确认。技术核验就绪不等于第三门禁通过；不把参数收集表交给客户填写，也不以笼统“是否继续”代替具体明细确认。复用前两门禁已确认事实，不重复索取地址、Token、应用身份、版本、架构或安装形态。

#### 都接入：两份明细与联合确认

完整展示上述更新、统计两套请求，不能只写“同上”、合并成一个请求或只列其中一项。补充 current_version/app_version 的共同真实版本来源、windows/macos/linux 与更新 OS 的映射、x64→x86_64/Windows ia32→x86/arm64→arm64 的实际目标映射、已有身份保留或新 UUID 共用规则，以及凭据、状态、调度独立和部分失败策略。客户确认须覆盖两项；只确认其中一项则只记录该分支确认，联合状态仍未通过，不暗中改变第一门禁范围。

### 明确确认与通过条件

技术核验后状态先记“技术就绪，待客户确认”。第一门禁范围选择、浏览器授权批准、读取配置成功或此前笼统“帮我接入”都不能代替对这份具体确认单的确认。回复正文展示完所选明细及待补项后，用可回答的确认问题收尾；有问答工具时通过工具提出，不能只停在记录链接或“未指定实施阶段”。

固定提问：**“请确认以上所选服务的请求地址、参数和实施方案。请选择：①确认并进入第四门禁；②仅确认方案，暂不实施；③需要调整（说明要改的项）。”** 无工具时在回复结尾提出同一问题。选项不是预先批准；等待用户明确回答，未回复或含糊回答不得开始依赖实现。

- ① 明确确认所列分支，并授权进入第四门禁；选择更新时先完成下述 UI 方案展示及客户确认，再编码，不能用第三门禁确认替代 UI 确认。仅统计且无可见 UI 变更时可直接按已确认方案实施。不要求再输入 Skill 名称或阶段编号。部署、真实业务请求、安装、发布等仍按独立授权执行。
- ② 只记录第三门禁确认，停止于方案，不写业务代码。已有“只读／不写代码”限制时，简单“确认”只确认明细；只有明确表示开始实施才改变该限制。
- ③ 修正受影响方案、重新展示具体差异和完整受影响请求明细，再等待确认；不能用客户同意绕过缺少真实端点/必填映射的阻断项。
- 已有明确本地实施授权且没有只读限制时，对当前完整明细的明确确认可以复用该授权。不存在授权时，单说“确认”不能推定同意业务实现。

第三门禁通过须同时满足：本次所选范围第二门禁整体通过、本节技术核验全部完成、完整确认单已在正文展示、客户明确确认全部所选请求明细。交接记录保存确认单版本/时间、展示依据、客户回复与覆盖分支、实施授权状态；不新增 Profile schema 字段。门禁状态按总表记录；技术结论另注明“技术就绪待确认”或“已确认待实施”，不将计划写成已接入。

同一确认单不重复确认；服务范围、目标应用/地址、固定参数、能力承诺或产品行为实质变更时，展示差异并重新确认受影响项。按已确认规则生成时间戳/事件 ID、读取运行时版本、凭据正常轮换，以及不改变合同和行为的内部实现调整，不触发重复确认。运行目标或版本通道发生影响选包的变化仍按实质变更处理。

仅对无法自动解决且影响正确性的产品身份/中文名称冲突、安装形态/发布目标不明、客户要求改变既有行为而无适用默认规则，提出最少必要问题。地址、登记、配置未录入或 Endpoint 映射问题优先核对可信运维资料；无法确认就列具体待补并停止依赖分支，不让客户贴密钥。没有可靠事实时不得默认 installed、伪造 APP_ID、域名、能力或产品名。

已知尚未登记、部署、发布策略或制品与“缺少接口合同/字段映射”分别记录：前者在目标与合同明确时允许本地准备，经第三门禁确认且有实施授权后才实现，后者阻断依赖实现。部署、构建安装、真实业务 E2E、发布、推送、购买和线上删除继续遵守各自边界。

## 第四门禁：客户端本地实施与验收

第三门禁技术核验与客户明确确认均通过后，第四门禁先根据当前项目 UI 风格准备并展示接入 UI、触发时机和显示位置，等待客户明确确认适用的 UI 方案，再在当前客户端已有实施授权内完成 Rust 实现、迁移与可复现本地验收。本次所选范围的第二、第三门禁必须整体通过；只要求方案或整理规范的任务不进入业务实施。门禁通过仅表示“本地实施通过”，不表示真实服务、GUI、制品安装或发布通过。

本门禁对应客户端本地实施责任，与原 CloudBase 运维“阶段 4：部署”不同；既有“阶段 5：客户端本地迁移”按本门禁分支清单验收，后续真实验证仍执行原独立阶段边界。机器入口只声明门禁，由 Skill 根据真实证据执行，bootstrap 不会自动完成实现或验收。

### 先展示并确认 UI，再编码

第四门禁内部依次为“UI 方案与位置确认 → 核实项目架构与编码规范 → 编码 → 本地验收”。第三门禁确认的是接口和接入方案，不代表客户已看过或批准尚未生成的 UI。仅更新、都接入必须先完成 UI 确认；等待期间只准备设计与独立预览，不提前修改业务 UI、Rust 接入、路由、依赖或配置，也不先偷偷实施统计分支。

#### 当前项目风格取证与预览

先读取当前目标项目已有页面、布局/导航、设置或关于入口、弹窗/通知组件、样式变量、字体字号、颜色、间距、圆角、按钮、图标和现有主题；复用实际组件体系及文案语言，不移植一套通用更新模板，不重做无关页面。列出取证文件/组件和已存在的 UI 证据；无法从现有材料看到运行外观时如实说明，不能声称已经运行或看过真实界面。原生 GUI 运行仍按既有授权边界执行。

必须给客户可见的普通更新提示、强制更新界面及手动检查入口在宿主页面中的位置预览，附状态与动作表；不能只描述“使用现有风格”或给实现文件路径。优先使用现有本地组件预览设施，或在隔离设计目录制作无网络、无业务调用的独立 HTML/静态图预览；不为预览安装依赖、接入真实接口或改业务源码。提供可打开的预览及正文中的图示/可视呈现，用当前产品名称和版本；目标版本、更新说明等尚无真实数据时标为“设计演示数据”，不冒充服务端响应。预览不能含凭据或原始安装身份。

只有合同和已确认能力支持的按钮/状态才能出现在拟上线方案中。尚未验证的拟新增能力单独标注；预览按钮不得真的发检查请求、下载或安装。若无法生成可查看的视觉预览，记录阻断原因，不能以一段文字宣称视觉方案已确认。

#### 三种范围与 UI 确认规则

- **仅更新**：展示普通更新、强更、手动入口预览及完整位置/行为表；客户明确确认后才编写更新前后端和配置，统计保持原状。

## 授权中心协议与配置字段

### 入口与凭据用途

本机 API 为 http://127.0.0.1:18080，同源代理 http://127.0.0.1:8090 同样支持全部 OAuth/配置接口；它们仅适用于服务所在机器。生产真实 HTTPS API origin、授权页 origin、client_id 登记及验证域名由可信运维资料提供，不能使用占位地址。更新配置要求 updater:config:read，统计配置要求 cloudbase:config:read（既有 audience ip-lookup-api，不发送 audience 参数）。持有对应 scope 的有效授权用户可以读取任意已配置 project_id，不要求管理员/项目归属；因此返回成功不证明它就是当前产品，应核对项目配置选择和下游应用登记。

OAuth access_token 为不透明字符串，不解析 JWT、不生成或修改。refresh_token 只刷新，device_code 只兑换，user_code 仅供用户授权。CloudBase SecretId/SecretKey、Updater ClientToken 都不是 OAuth access_token/client_secret。令牌和密钥原文保留，不 trim；发现不符合下游要求则停止该分支，不自行修复。

### 三种范围的 scope 与实际授权

| 第一门禁范围 | 设备申请 scope                              | 所选配置权限      |
| ------------ | ------------------------------------------- | ----------------- |
| 仅更新       | `updater:config:read`                       | 只 GET Updater    |
| 仅统计       | `cloudbase:config:read`                     | 只 GET CloudBase  |
| 都接入       | `cloudbase:config:read updater:config:read` | 两个 GET 分别校验 |

多个 scope 用单个 ASCII 空格连接，大小写敏感、最长 128 字节，不允许空集合、重复项、首尾/连续空格、制表符、通配符或 resource:read。ip:read 仅授权 IP 查询及代理详情，旧 ip:read 令牌不能查配置，刷新也不会增加权限，需重新授权。

客户端 allowed_scopes 只表示允许申请的集合；新登记省略时默认三项不代表自动获授。设备申请只决定浏览器初始勾选，用户可增选/取消客户端允许项。令牌响应 scope 才是实际获授集合，按集合解析且比较不依赖顺序。复用前核对环境、client_id、有效期和权限；缺权限不能通过刷新补齐。

用户取消某项权限时停止该已选分支，需要继续时重新授权，不循环申请；已有权限分支只完成当前第二门禁的配置读取和校验；联合第二门禁未全过不得进入第三门禁。用户额外勾选权限不扩大第一门禁范围，不调用未选配置 GET。浏览器批准和业务接入选择分别记录。

### 申请设备码与浏览器授权

POST `/oauth/device/code`，Content-Type `application/x-www-form-urlencoded`，Accept `application/json`；表单只有 client_id 与按上表选择的 scope，不发 JSON、不发 client_secret。

HTTP 200 裸 JSON：device_code、user_code、verification_uri、expires_in、interval；verification_uri_complete 可选。当前实现返回完整授权 URL；缺省时按下述回退处理。校验非空字符串、正数秒数并记录截止时间。优先打开 verification_uri_complete，缺省打开 verification_uri 并展示 user_code；打开前验证其 origin/路径匹配可信部署授权页，不能从不可信响应扩宽允许域名。只展示短码，不展示 device_code，不把 token/机器码放入 URL。浏览器负责登录、Cookie、CSRF、必要改密/风控确认和批准；Skill/客户端不收密码、不调用 /device/verify、不自己实现登录表单。

expires_in 与 interval 均取响应秒值，不硬编码文档演示的 600/5。首次轮询至少等 interval；批准后及时兑换，当前批准后的兑换窗口最多 60 秒且不超过原截止。

### 兑换与轮询错误

POST `/oauth/token`，表单编码，Accept application/json；设备码分支只发 client_id、grant_type=`urn:ietf:params:oauth:grant-type:device_code`、device_code。不附加 scope 或 refresh_token。

HTTP 200 裸 JSON 六字段：access_token、token_type、expires_in、refresh_token、scope、user_id。确认 token_type=Bearer、实际 scope 包含对应已选服务权限、令牌非空，expires_in 取响应正数秒值，不写死 300；令牌对、实际 scope 和到期时间整体安全保存，不以申请 scope 覆盖响应。user_id 不进入 Profile/日志。成功立即停止轮询，设备码只能成功兑换一次。

| HTTP / error                                         | 行为                                                         |
| ---------------------------------------------------- | ------------------------------------------------------------ |
| 400 authorization_pending                            | 等当前 interval 后继续                                       |
| 400 slow_down                                        | 当前服务每次增 5 秒，上限 30 秒，同时遵守 Retry-After        |
| 400 access_denied                                    | 用户拒绝，停止，不反复申请                                   |
| 400 expired_token                                    | 设备码/兑换窗口过期，停止，需要时重新授权                    |
| 400 invalid_grant                                    | 无效、已消费或授权失效，停止后重新授权                       |
| 400 invalid_client / invalid_scope / invalid_request | 核对登记和表单，不要求客户编造值                             |
| 429 rate_limited                                     | 停止当前自动循环，按 Retry-After 稍后再试                    |
| 网络失败或 5xx                                       | 不视为成功；兑换可能已消费，不能无限重试，无法恢复则重新授权 |

### 两个配置接口

### 刷新与撤销

刷新 POST `/oauth/token`，表单为同一 client_id、grant_type=refresh_token、refresh_token；默认省略 scope，不传 device_code。省略 scope 延续实际获授集合；若传入，必须与原获授集合完全相等（顺序不限），不能增加或缩减，也不能直接沿用可能被用户改选的申请值。invalid_scope 核对集合或省略字段，调整权限须重新设备授权。成功与设备码兑换同形，返回新令牌对。可按响应到期时间提前约 30 秒刷新（短有效期不能因此形成循环）。同一授权在请求/进程间串行刷新，成功后原子替换 access_token、refresh_token、实际 scope、到期时间；旧 access_token 立即失效。

当前刷新宽限 10 秒；旧 refresh_token 不进通用重试队列。响应丢失时，仅能确认仍在首次发送后 10 秒内才允许一次受控恢复，否则重新授权；invalid_grant 清除本地令牌并重新授权。不能把该 OAuth 刷新当成 Updater ClientToken 刷新，更新中心自身仍没有此处定义的令牌刷新接口。

解除连接或适用的退出流程可 POST `/oauth/revoke`，表单 client_id、token=当前 refresh_token、token_type_hint=refresh_token，Accept application/json；成功 200 裸对象 revoked=true，随后清除本地令牌。仅退出浏览器不等于撤销 OAuth。一次性接入授权结束按生命周期清理；不能因保存了浏览器 Cookie 就宣称后续配置访问仍获授权。

### 仍需部署核验的事实

- 生产授权中心真实 HTTPS origin、授权页地址、适用的 client_id 登记；本机联调地址不能推广到其他机器。
- 当前 project_id 的真实配置读取是否成功；文档历史回执不代替本次 200 响应。
- CloudBase Endpoint 是何种服务端点、如何对应既有日活网关和路由；依据响应、登记及获授权只读部署资料自动核验，不能从 EnvId/Region 拼出未经证明的域名。
- Updater Endpoint 的路径形式、应用登记及实际下游允许列表一致性；配置 API 的宽长度限制不覆盖下游限制。

以上是部署事实核验，不再要求客户提供已定义的 OAuth 协议、字段 schema 或手填密钥。缺少事实时停止对应分支并报告准确原因；本 Skill 规范更新本身不执行真实授权、配置请求、云端写入或业务代码修改。

## 接入流程与验收证据

第一门禁后自动识别项目并进行第二门禁设备授权/所选配置读取，再通过第三门禁客户端方案核验，进入第四门禁在原授权内实施并本地验收。源码、Profile 草稿或 mock 成功不代替真实取配置；不要求客户手填技术参数，但必须经过第三门禁完整请求明细确认及第四门禁适用 UI 确认。

先过接入范围确认门禁，再按所选服务执行下面流程。仅更新跳过日活配置/实现/验收，既有日活保持原状；仅统计跳过全部更新配置/实现/清理/验收，既有更新保持原状。未选择的部分标为“不在本次范围”，不列作缺失必填项。

接入按以下顺序定义责任，不要求本次“整理规范”任务实施业务代码：确认应用/版本/目标和本地状态 → 按真实合同获取运行时配置 → 校验服务地址与应用/凭据绑定 → 独立执行日活门禁 → POST 更新检查 → 校验完整响应后展示/决策 → 下载并校验大小和摘要 → pre_install 新建检查并对照目标 → 固定本地适配器安装 → 重启后核实真实运行版本。

| 验收项     | 需要的证据                                                                                               |
| ---------- | -------------------------------------------------------------------------------------------------------- |
| 配置获取   | 与正式请求/响应 schema 一致；缺失字段、错误应用、非法地址与鉴权失败不误用；配置未取得/未验证时不标记完成 |
| 请求参数   | 实际序列化请求，版本/系统/程序架构/通道/安装形态来源可追踪，凭据仅证明存在不保存值                       |
| 日活门禁   | 首次发送、同日/并发不重复、失败不补发、自然新日恢复、升级保留身份及门禁                                  |
| 响应       | 201 与错误分离；完整字段、可空、枚举、范围和组合校验；失败不冒充最新版                                   |
| 平台匹配   | 每个真实发布目标独立验证，Windows x86 使用 x86/ia32 映射，不支持的组合被拒绝                             |
| 强更与离线 | 不可更新不新增阻断；保留既有任务、更新/重试/退出；过期/重启/时钟异常不意外永久锁死                       |
| 下载       | 跳转不泄露 Token，长度/摘要不符不执行，过期检测重新 POST                                                 |
| 安装前复检 | 新检测 ID，目标版本/包 ID/大小/摘要/action 仍匹配，当前版本取实际运行值                                  |
| 安装成功   | 精确制品哈希、进程/窗口、重启后实际版本；HTTP 或编译成功不能替代                                         |
| 隔离与迁移 | 本应用状态/路由/集合独立，已授权范围无旧更新回退，不删除其他应用或线上旧资源                             |

本地 mock、静态检查、编译、生产 HTTP、真实制品 GUI E2E 分别记录；未验证的平台保持 Unverified。仅字段清单齐全、Profile 通过或 SDK 分发成功不能证明真实接入完成。

## 现行运行时

### Telemetry

- 固定事件 `daily_active`，同一匿名安装在北京时间当天最多尝试一次。
- 联网前原子落盘；失败当天不重试、不排队。
- 每个应用使用自己的 APP_ID、AppConfig、本地身份、函数、路由和集合。
- 客户端不发送 IP，不采集账号或硬件指纹。

### 三类版本信息

| 信息           | 来源与用途                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `app_version`  | 当前已运行应用的 SemVer，随既有 `daily_active` POST 发送，用于客户端活跃版本画像。宿主通过 SDK 的 `appVersion` 提供；缺失或非法值会被拒绝。 |
| `sdk_version`  | 现行日活合同固定为 `3.0.0`，服务端等值校验；不能填 Rust crate 或自行选择的适配器版本。应用版本碰巧相同合法。                                |
| `code_version` | 运营端管理接口维护的发布记录，位于逐应用 `versions_*` 集合，按发布流 code 读取，决定看板“最高版本”和更新策略。                              |

Profile `current_version` 只记录实施时快照；真实运行值应由 `version_source` 所指的发布配置/制品版本提供给 telemetry 和版本检查。升级后不需要改接入代码、Profile 或固定常量才能上报新版本。检查两个入口满足各自版本格式约束；格式冲突时报告，不私自截断或填 `0.0.0`。保持原 `daily_active` 十字段协议，不增加版本上报事件或额外字段。

阶段 5 必须在本地注入 transport/fetch，捕获序列化请求并比对应用版本；换一个来源版本值后使用新的测试日期重验，证明不是写死的值，且同日升级仍不多发。通过后记录 `telemetry_app_version_verified=true`，它不证明真实制品已经上报。阶段 6/7 的 `telemetry_app_version_online_verified` 必须来自已授权真实客户端和服务端接受证据：绑定制品版本与哈希，应用版本和已接受请求一致，核对看板相应平台/架构的活跃版本画像；既有同日门禁已领取时等待正常新日，不重置生产状态。只保留脱敏的版本比对证据，不保存安装标识、IP、原始凭据。

Telemetry 上报和更新检测都不发布版本。历史运营看板的 `code_version` 来自旧版本服务的发布记录；新更新中心另有自己的发布数据，不能把客户端观测值当作可供下载的正式发行版。

### 客户端更新中心

新客户端调用 `POST {已确认的服务 origin}/api/v1/apps/{app_id}/update-checks`，当前 Profile 允许的生产 origin 为 `https://update.meetelf.com`，地址由授权中心配置的 Endpoint 提供，ClientToken 用于下游 Bearer，不能忽略响应使用内置默认值。使用运行时客户端 Bearer Token，按真实版本、系统、程序架构、安装形态、持久随机 UUID、通道和已实现能力发请求；仅 201 解析决定。完整处理、强更、下载、安装前复检、离线策略和验收见 [客户端更新中心接入合同](client-update-center.md)。

旧 application-version 的 GET 协议仍用于既有运营服务，不作为新客户端接入协议，也不因迁移客户端而自动删除云资源。

## 完全删除旧版本协议

基础设施 3.0 不承认旧静态更新为有效 transport。迁移时删除：

- 静态更新 Base URL 和平台 manifest URL；
- 14 字段 manifest types/parser/schema；
- rollout、min-supported、旧 force-update 决策；
- fallback、dual-read、兼容开关；
- 旧协议专用源码、夹具、测试和现行文档。

不要删除可复用的严格 SemVer、安全公网 HTTPS URL、纯文本 UI、主窗口异步时序、外链或完整退出逻辑。

## APP_ID 和隔离

APP_ID 用于隔离 telemetry 和更新中心中的应用身份。telemetry 仍派生 `telemetry-<app_id>` 函数、`telemetry_<normalized_app_id>` 集合和 `/apps/<app_id>/v1/track` 路由。新更新服务按实际 `os + architecture + installation_type + channel` 匹配；`x64` 映射为 `x86_64`，Linux 使用实际 Ubuntu 或 Debian。历史 CloudBase versions、ads、audit 集合及 code 仍由现有运营服务管理，不得作为新更新服务的配置或在此阶段删除。

CloudBase 资源登记约束为 `^[a-z0-9](?:[a-z0-9-]{0,48}[a-z0-9])?$`（1～50）；Updater 为 `^[a-z][a-z0-9-]{2,63}$`（3～64）。新联合接入同一 ID 使用交集 `^[a-z][a-z0-9-]{1,48}[a-z0-9]$`（3～50）；这不是改写单个服务合同。已有身份冲突须报告，不自动重命名。Windows 的 telemetry ia32 对应 Updater x86，其余系统不得用 x86 更新目标。

## Profile v2

路径固定为 `.bifang/public-services-profile.json`。新接入设置 `update_transport=client-update-center-v1`、生产地址 `update_center_base_url=https://update.meetelf.com`、非敏感 `update_center_auth_status`、按真实目标填写的 `update_targets`，并明确 `offline_enforcement=service-default|persist-until-resolved`。明确要求本地联调时地址可用 `http://127.0.0.1:8080/`；仅本地证据不能标记生产服务及客户端 E2E 已验证。后一项策略仅用于产品负责人明确要求的离线持续强更例外。

继续保存确认的中文 `display_name`、APP_ID、版本来源、telemetry 信息、运行时钩子、门禁及阶段；不得存 Token、凭据摘要、硬件 ID 或绝对路径。旧 Profile v1/v2 先只读核验，迁移到新 transport 时删除客户端旧协议字段，不把旧 code 当作新接口目标。

## Profile 写入

1. 先只读解析现有 Profile；重复字段、非法 JSON 或敏感值立即停止，不覆盖。
2. 用当前代码证据重新核对已有事实；冲突必须展示。
3. 规范 URL 一句话已经授权阶段 1，可写确定性的 v2 非敏感档案；仍无法确认的产品事实最多问三个短问题。
4. 写后运行 `validate_profile.py <profile> --require-update-center` 和 `derive_resources.py`。
5. 只有生产代码/配置和活跃测试均无旧静态协议且扫描完整，才写 `legacy_update_status=removed` 与相应 gate。

中文名为 1–100 个 Unicode 字符，包含中文，无首尾空白、控制/格式字符或 `<`、`>`。从发布产品配置、窗口标题或负责人说明确认；不得把 npm 包名、仓库名、APP_ID 当作显示名，也不得自行翻译或猜名。旧 Profile 缺名或只含英文时，在已授权 Profile 修改范围内按证据补全并重新校验；草稿可暂缺名称，但不能标记完成。`derive_resources.py --profile` 要求有效名称，并输出 `display_name` 与 `dashboard_app_labels` 作为交接证据；只给 APP_ID 的技术资源预览不代表名称已经确认。

运营精灵阶段 2 将该映射写入唯一名称表 `cloudbase/functions/operations-dashboard/src/app-labels.json`，并运行 `npm run cloudbase:labels:check -- --profile-file "<已校验的 Profile 交接文件>"` 后，才可写 `app_display_name_registered=true`。命令同时核对精确名称、APP_ID 登记和完整名称覆盖；该 gate 不证明线上已生效。`dashboard_display_name_verified` 只在已授权部署后的已登录接口和页面实际显示正确中文名时为 true；没有生产验证时保持未验证。两个 gate 的证据不得互相替代，客户端本地阶段 5 仍不依赖云端完成。

旧档案的 `app_registered` 只证明既有技术登记，不证明中文名已登记；缺少名称证据时保留新 gate 为未验证，不能直接补成 true。阶段 5 可保留这一真实状态并完成本地迁移；阶段 3/4 及真实客户端验收、发布阶段分别补齐相应名称证据。

## 凭据

更新中心使用运行时客户端专用 Bearer Token，不能用后台管理凭据；其共享值可从客户端提取，不代表用户身份。不得写入 Git、Profile、命令行、普通日志或证据。本地验收使用假 transport 和假凭据；这不豁免第二门禁的真实授权与所选配置验证，线上状态仍须独立证据，否则保持 `Unverified`。

## 阶段门禁

- 阶段 2：APP_ID、更新目标和中文名已确认；登记表无冲突，统一名称表与 Profile 一致，完整名称覆盖检查通过。没有真实旧发布流时由运营精灵使用 `npm run cloudbase:app:add -- <app_id>` 登记仅 telemetry 资源，不编造旧 code。
- 阶段 3：生成 telemetry 配置包含全部已登记应用；`app_display_name_registered=true` 有实际校验证据；更新中心目标及费用计划已审查。
- 阶段 4：最新远端只读预检、费用为零、写入目标精确，等待明确“继续”；完成后核对线上应用集合、中文名及全部发布流，才标记 `dashboard_display_name_verified=true`。
- 阶段 5：服务端契约可本地测试；当前客户端替换/删除旧实现，本地实际请求证明应用版本来自唯一来源，`telemetry_app_version_verified=true`。
- 阶段 6：服务公网已验证、运行凭据已就绪；准确新构建制品的真实 GUI E2E 与已接受 `app_version` 一致，才标记 `telemetry_app_version_online_verified=true`。
- 阶段 7：隐私、签名、制品、下载地址、回滚均就绪，发布/推送前再次确认。
- 阶段 8：两个客户端新协议 E2E 完成，最新枚举证明旧云资源可删，展示精确目标后再次确认。
