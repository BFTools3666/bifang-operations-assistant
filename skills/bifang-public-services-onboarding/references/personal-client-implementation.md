# 第四门禁：先确认 UI，再按项目规范实施

本门禁适用于客户目标项目中的客户端接入。只要求维护 Skill 时，只修改规范和检查，不运行客户门禁、不制作客户业务页面、不写业务接入代码。这里定义实施流程，不代表本仓库已完成某个客户的接入。

## 前置证据与严格顺序

进入前核对本次前三门禁通过记录、已选范围和第三门禁 confirmation_id；通过本地受控进程核对其私有 input_binding 与当前输入/所选凭据一致，不把原值或摘要输出。请求、版本、平台/code、范围或默认行为改变时返回第三门禁更新对应明细并重新确认。客户只确认参数不等于已经确认 UI。

| 检查点            | 必须完成的事                                                              | 通过条件及产出                                                                                |
| ----------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 4A UI 预览与确认  | 阅读当前 UI，展示普通更新、强制更新、手动入口和触发位置，等待客户明确确认 | 可见预览、位置/交互表、强更限制清单及客户对本版 UI 的明确回复；仅统计无可见变更按下文记不适用 |
| 4B 架构与规范核验 | 阅读目标项目规范及实际调用链，确定复用方式、修改边界和检查命令            | 有文件依据的实施摘要与可执行验证计划；这是自动核验，不新增人工审批                            |
| 4C 本地实施       | 在已授权的范围按已确认请求、UI 和项目规范编写代码                         | 选中服务的实际实现、必要迁移及本轮问题修复；不得用计划冒充完成                                |
| 4D 本地验收       | 使用假凭据、模拟传输和临时状态执行适用检查                                | 所选项检查通过，交付变更、验证结果及未执行事项；仅标本地通过                                  |

四个检查点严格串行，上一项未通过不得进入下一项。两项都接入时，等待更新 UI 确认期间也不能先实现统计；4D 两项及联合检查均通过才通过整个门禁。已有有效证据复用，不重复问可自动确定事项。

客户已要求“接入/实施”的情况下，UI 明确确认后，完成 4B 即按已有授权直接编码，不再问“是否开始”。如果本次仍明确限于文档、预览或“暂不实施”，UI 回复不能默认解除限制；把已确认方案交付并停在编码前，只有客户明确改变该限制后才继续。不因维护本 Skill 的指令而开始修改任何客户项目。

## 4A：从真实项目风格形成可见方案

先读取目标项目根目录及预期修改目录的 AGENTS.md，观察已有页面、导航、主题变量、字体、颜色、间距、圆角、按钮层级、弹窗/通知组件、图标、暗色主题、键盘焦点及错误提示方式。以当前源码和已有可见界面为依据，引用具体文件；能直接查看的不要再让客户描述。项目没有某个页面时如实记录，不假造“已有设置页”。

优先复用现有组件与设计变量，制作与目标项目风格一致的可见预览。可采用隔离的静态/交互原型、项目支持的独立预览或图片；用模拟数据，标明“UI 方案预览，未接入真实接口”，不得借预览提前改生产入口、加入业务调用或依赖真实凭据。只有文字说明、流程表、组件名、文件路径都不能代替可见预览；无法提供预览时记录阻碍并停在 4A。

对选择更新的任务，至少把下列三类界面展示完整，状态变体可合并展示，无需强制提供多套设计：

| 界面               | 展示内容、位置和行为                                                                                                                                                                | 客户要确认的内容                                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 普通更新           | 按项目已有弹窗/侧栏/通知承载，列具体页面和组件位置；显示当前真实版本、更新提示和内容，主按钮默认“前往下载”，次按钮“稍后”；允许关闭/Esc，不限制业务                                  | 视觉样式、文案、显示位置、按钮和关闭行为、主动提示与手动检查的区别                     |
| 强制更新           | 在主窗口已有阻断容器或明确的新位置显示“需要更新”；默认提供“前往下载”“重新检查”“退出应用”，不提供“稍后”，关闭/Esc/遮罩不能绕过确认的限制；仍保留已有任务查看、必要控制和安全退出通道 | 强更出现的位置、按钮、关闭行为，以及逐项列出的新业务限制；不能用“禁用全部操作”代替清单 |
| 手动检查入口及结果 | 复用真实已有“关于/设置/帮助”等位置，给出实际导航路径和入口预览；没有时提出最符合现有导航的入口并随 UI 一起确认。展示检查中、可更新、无需更新、失败/重试状态；检查中防重复触发       | 入口路径、显示文案、加载状态、结果位置、错误反馈和重试行为                             |

普通与强更均应适配项目已有主题、窗口尺寸、滚动和键盘焦点规则。更新文案默认按纯文本或现有受信清洗机制显示，不将服务端富文本直接注入页面。预览和交接记录不包含密钥、账号或真实安装标识。

### 触发条件与实际位置一并展示

每个触发点注明“触发时机 → 请求入口 → 结果显示位置 → 按钮/关闭行为”，用目标项目真实页面与调用位置填写，不能只写“启动时/弹窗”。

| 触发点          | 默认方案与核验项                                                                                                                                                                            |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 启动            | 应用 UI 就绪后后台检查一次，复用现有生命周期与异步机制；不阻塞初始化。普通自动提示只在有效 update=true、promptUpdate=true、forcedUpdate=false、stopUpdate=false 时出现                      |
| 强更            | 有效响应满足 update=true、forcedUpdate=true、stopUpdate=false 才展示强更并应用已确认的新业务限制。按具体窗口/容器和业务命令列出作用范围                                                     |
| 手动检查        | 用户从已展示入口触发，等待时禁用重复提交；update=true 且非强更时可以显示普通可更新结果，即使 promptUpdate=false。update=false 显示“当前无需更新”，不能在 stopUpdate=true 时宣称当前是最新版 |
| 定时检查        | 第三门禁基线默认关闭，明确标“不启用”。确需启用须先更新第三门禁行为并确认，再展示间隔、生命周期、可见提示和去重，不静默增加定时请求                                                          |
| 前往下载        | 用户点击后经 Rust 核验有效 HTTPS 下载地址，使用项目既有安全打开方式交给外部浏览器；不携带 API 密钥，链接打开失败在当前界面反馈。打开网页不等于下载/安装完成                                 |
| 安装前/更新完成 | 当前基线没有应用内安装流程，此触发点标不适用；不展示虚假下载进度、“立即安装”“安装成功”或自动重启。重启后可按真实运行版本重新检查，不能仅因点击链接就解除强更或报告升级完成                  |

协议仍是第三门禁已确认的 application-version-api 七字段响应；没有 latestVersion、signature、sha256 或 block_new_operations，不添加这些字段判断或假造目标版本。只有合同完整、有效的响应才产生更新状态；未发布版本的 404、鉴权失败、网络错误、超时或坏 JSON 不能显示“已最新”或新建强更限制。已经有效进入强更后的重试失败不当作解除依据，保留原提示、重试和安全退出，不扩大限制；有效响应不再要求强更时可解除本次限制，但不能据此声称安装成功。

默认只限制用户确认清单中的**新业务发起**，已有任务继续执行，已有数据不删除，不强杀进程或后台任务。若任务查看/停止/保存操作因阻断界面不可达，方案必须先修正，不能以强更为理由丢失这些通道。具体边界无法从项目识别时，说明冲突并在 UI 确认中最少澄清，不能自行扩大限制。

### UI 确认记录

正文展示预览并列出：样式来源文件、三类界面、实际触发/显示位置、按钮/关闭行为、强更限制及保留的操作、所用默认值和未实现能力。给本次 UI 方案一个版本标识，关联第三门禁 confirmation_id，提示客户确认这版 UI 与触发位置。客户此前的参数确认、“已填写”或未回复不算 UI 确认。

记录客户原话和预览版本，确认后才能进入 4B；布局、入口、触发方式、关闭行为或强更限制实质变化时重新确认受影响 UI，涉及请求/默认行为时同时返回第三门禁。普通代码修复和既定方案内的实现细节无需重复审批。

## 按所选范围执行

| 范围       | UI 阶段                                                                                                                                         | 实施与本地验收范围                                                                      |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 仅更新     | 必须展示普通更新、强更、手动入口及位置，等待明确 UI 确认                                                                                        | 实施更新请求、状态、已确认 UI 和入口；保留现有统计行为，验证没有额外统计请求            |
| 仅统计     | 默认无打扰、无可见 UI 变更时，记录“4A 人工确认不适用”及项目依据，不为统计创建更新 UI。若新增/改变隐私说明、开关或可见状态，先展示对应界面并确认 | 按十字段、安装身份、北京时间原子每日门禁实现后台上报；保持现有更新行为                  |
| 更新和统计 | 更新 UI 必须先确认，统计若有可见改动一起展示；等待期间两项都不编码                                                                              | 两项均实现并验收，再验证独立调度、状态/凭据隔离、部分失败和互不阻塞；统计不复用更新凭据 |

## 4B：编码前学习项目架构与规范

UI 确认适用项通过后，完整读取目标项目及所有拟修改目录适用的 AGENTS.md、架构/编码文档、构建与测试配置，再跟踪实际模块调用链和至少一处相关同类实现。不能仅根据目录名或 Tauri/Cargo 标识套模板。

实施摘要需要有具体文件依据，覆盖：

- 前端页面/组件、状态管理、导航与 Rust 命令/事件边界；可复用的 UI 组件与样式。
- 启动生命周期、HTTP 客户端、配置/凭据存储、版本与平台来源、异步调度、取消、错误类型、脱敏日志及状态持久化方式。
- 模块职责、依赖方向、文件位置、命名、格式、已有测试惯例；本次拟改文件/模块、旧实现的处理范围和实际验证命令。
- 与第三门禁请求、默认行为和本次 UI 的对应关系，必要的旧接入迁移，以及未选服务如何保持原状。

保持项目现有架构和前端栈；Rust 负责可信网络请求、凭据读取、协议校验、版本/身份/每日状态和安全链接检查，前端只接收必要的脱敏业务状态，不接收运行时密钥，更不接收 CAM 或管理凭据。按项目现有模块边界组织，不强制迁移到服务端模板，不顺带重构无关模块。

如果项目没有规范文档，根据已存在的相邻实现归纳并注明依据；能自动决定的目录、组件、错误风格和测试命令不再问客户。缺少 Rust 接入层或架构冲突导致无法在已确认范围内实施时，先给出具体差异与最小方案，不能悄悄更换技术栈或伪造“已核验”。摘要说明后按有效授权直接进入 4C，不单独等待“架构批准”。

## 4C / 4D：授权内编码、验证与交付

只实现本次已选服务、已确认参数和 UI；必要迁移限于目标项目选中模块，不删除云端旧资源或改变其他客户。使用项目已有的私有配置/安全存储机制读取必要 runtime 凭据，不将密钥原值写入源码、打包资源、前端事件或日志。第三门禁私有实例是参数证据，不能作为应用自动执行的请求脚本或直接整体分发。

在本地采用假凭据、可注入的传输、固定时钟和临时状态，运行目标项目要求的格式、静态检查、单元/组件/模拟集成检查并修复本轮失败。使用本地 mock 的可见 UI 核验可以纳入已授权本地验收，但不得由预览/启动开发环境间接请求真实服务、写真实日活或修改生产状态。测试必要的编译可随本地检查执行，不默认授权制品打包、签名、安装或真实 EXE 验收。

| 验收分支 | 必须核验的实际行为                                                                                                                                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 更新     | 正确 GET 路径与两项 runtime 请求头，无多余 query/body；正常提示、手动结果、强更及恢复、stopUpdate、update=false；404/401/403/429/超时/坏响应不误判；启动和手动去重、外部链接校验/失败反馈；限制只覆盖已确认的新业务入口，已有任务可继续；没有虚构安装能力或暴露密钥 |
| 统计     | 精确十字段和真实版本/平台映射；每应用随机持久身份、事件 UUID、原子北京时间每日最多一次尝试、并发和跨日行为；失败后台处理且不立即重试；无客户端密钥、账号/硬件字段或预览身份混入；不影响更新                                                                         |
| 联合     | 更新失败不阻止统计，统计失败不影响更新；凭据、状态和调度隔离，不互相复用安装/请求状态；两个分支及联合检查全部通过                                                                                                                                                   |

未能执行的适用检查、缺少的平台或依赖如实记录，不能直接标整个第四门禁通过。交付包含各检查点证据、UI 版本和确认、架构摘要、实际变更、真实执行的命令/结果、问题与未执行项；只有产生提交才报告提交哈希。状态只能是“本地实施与验收通过”或明确未完成项，不冒充云端、网页、下载、安装或真实用户接入成功。

真实 HTTP/云端测试、统计写入、版本发布、云资源/权限变更、制品构建打包/签名/安装、真实 EXE、推送发布及删除仍需具体目标动作授权；已有覆盖同目标的授权复用。涉及部署/发布/推送/删除时按现有边界展示最终目标与最新预检结果后确认，不把 UI 确认扩大成这些操作授权。

本地通过后进入 [第五门禁](personal-update-preflight.md)：客户补齐发布信息，助手本地校验并展示具体保存计划；确认后自动保存、管理读回并做已说明范围内的更新 GET 预检。预检失败停留第五门禁，由客户调整后重检，通过后才进入第六步 EXE 测试；仅统计记更新部分不适用。当前第四门禁不执行真实预检或制品测试，不自动接回公司版更新中心流程。
