# 已接入应用的版本更新管理

客户选择「2. 更新版本」，或说“已接入，想更新版本”“查看 Windows 当前更新”“把推荐改为强制”或“取消这次更新”时走本流程。继续既有首次接入任务中的第五门禁仍按该任务执行。“升级 Skill”指向技能安装维护。结合客户对象和会话上下文判断，仍有两种合理解释时，展示主入口的两个编号选项并等待选择 只要求设计规范或举例时用模拟信息。

## 大屏自助发布

本流程涉及客户操作云端时，在当次提示逐项展开[官方页面指引](../assets/console-guides.json)中适用的 domain、routes、functionConfig：给可点击入口、页面内位置、目标字段或操作和完成标志。

客户希望在页面提交时，先用该环境的部署记录、当前大屏页面和服务端接口核对「版本管理」是否可用。已部署时给客户真实大屏地址和页内入口。当前源码随附发布页和版本服务处理程序。使用[安装与升级](dashboard-install.md)区分未部署服务、旧代码和缺少后台绑定。已上线的入口位于实际大屏路径下的 `releases`。

**同一次登录管理整个后台。** 使用现有大屏会话，登录者可以管理此后台全部已接入应用和发布流。无需为客户建角色、分配应用权限、开通发布资格或再次登录。后端每次读取或写入均验证有效会话，并从本环境已登记的应用、平台、架构和通道映射到准确的 code。网页写请求须校验同源、防止跨站提交。大屏通过同环境 Node SDK 调用固定的版本服务函数。版本服务核对后台绑定摘要、应用和已登记发布流，复用事务仓储并写入审计。浏览器只使用登录会话。

1. **看当前设置。** 用中文应用名和平台、架构、通道展示各发布流的最高版本、推荐／强制／停更／仅手动状态。单一目标自动选中。有多个平台时明确勾选本轮目标，展示每个平台原有的版本、文案及下载地址。
2. **只填本次变更。** 查看详情直接展示。发布新版时填写版本号、各目标的 HTTPS 下载地址并选择策略；必填的提示文案由系统预填供客户修改，详细更新说明选填。推荐与强制互换、取消或恢复更新时复用现有记录。重新设置时预填完整旧值，仅改客户所选字段。取消通过现有记录的停更开关生效。
3. **预览并确认一次。** 服务端校验输入并生成逐平台差异，页面显示应用、发布流、版本、改前改后及对客户端的影响。点击「确认生效」即确认本次具体变更。多平台可以一起确认。表单、目标或远端记录发生变化时，刷新受影响的差异。复用第五门禁时，页面若仅说明发布，已有的预检、构建及实机操作授权仍按原范围核对。
4. **写入并读回。** 服务端复用版本管理 API，逐目标查重、复核当前记录，再新增或按实际 id 修改。相同提交只执行一次。写入结果不明先读回；多平台部分成功时，只处理仍待核验或失败的目标。页面分别展示写入与管理读回结果，提供带目标、变更和记录 id 的回执。运行时效果按实际客户端版本另验。

页面实施验收使用模拟版本服务覆盖未登录及过期会话拒绝写入、登录后跨已登记应用切换、跨环境或未知目标被拒绝、推荐改强制、取消、重复提交、并发变化和部分成功。真实环境优先复用已确认发布的回执并只读核验。首次接入第五门禁和日常发布共用一次提交。

网页与私有设置文件共用 `release-form.js` 生成 release 草稿、校验字段、判断新增或修改。新发布默认预填应用中文名、发布流、推荐模式和“有新版本可用。”，版本、下载地址和详细说明留空，条件默认为全部旧版本。重新设置时带入完整原值：同版本（含等价点分写法）修改原记录，更高版本新增，较低版本提示修改。沿用原下载地址新增版本时，预览中提示核对制品。发布名称可调整，发布流由所选目标确定。单选的推荐、强制、停更、仅手动依次映射至对应布尔项，选仅手动时三项均为 false。清除适用条件时同时移除条件及比较版本。字段不合法时保留输入并指出需要修正的字段。快照、确认摘要和凭据由办理入口管理。

## 对话办理

客户选择对话办理，或其部署尚无发布页时，由助手执行以下步骤。工具在已定位源码的 `cloudbase/personal/release-management.mjs`。参数示意在执行时换成真实值，向客户交接文件时给实际绝对路径和可点击链接。使用仓库已安装依赖，私有文件沿用接入任务的受限目录。

## 1. 查当前状态

输入为本次应用和发布流（平台、架构、通道）、实际待检查客户端版本、对应环境的已确认接入材料。复用第三门禁的 integration-input.json 和该 confirmation_id 对应的私有请求实例，核对客户确认记录及真实部署地址。客户原话中的平台名称可直接作为 --platform 条件，架构与通道分别用 --arch、--channel。唯一匹配时工具直接采用；多个匹配或无匹配时只回传已绑定的平台、架构和通道选项，请客户一次选定范围。助手按工具返回的 choice 显示发布目标，筛选后保留原编号，再将选中的平台、架构和通道映射到 code。多个明确目标分别查。项目当前版本有变化时从当前项目或客户信息取值，显式传入 --current。

```text
node cloudbase/personal/release-management.mjs inspect --input <接入文件> --evidence <已确认请求实例> --code <目标发布流> --current <实际客户端版本>
```

工具用 managementRead 分页查管理列表，按 app/code 筛选，按数字点分版本取最高记录，再用 runtime 做一次该客户端版本的 GET。输出含核验时间的私有状态文件、目标平台、发布版本、三项开关和客户端实测判定。未知目标、列表不完整、凭据不匹配、运行时与管理记录不符时报告无法判定及缺少的依据。只有管理列表完整且本流确无记录，结合已确认路由的运行时返回，才报告尚未设置更新。旧项目若缺少本工具所需的绑定文件或托管凭据，先用客户已有的部署资料核实 URL、发布流及对应角色，按同一 API 和私有文件规则做限定读取；只补缺少的证据。只有实际需要接入客户端时转首次接入。

若返回 runtime-unverified，先交付管理列表中已核验的配置、运行时失败项和查看时间，把客户端实际效果标为待验证。助手用已有目标和凭据处理可恢复故障并重新 inspect，在运行时证据完整后再生成写入计划。此时客户无需重填发布信息。

向客户分别说清**远端设置**和**这版客户端的结果**。最高记录的 forcedUpdate、promptUpdate、stopUpdate 中最多一个为 true，分别表示强制、推荐、停更。三项均 false 是有更新时仅手动可见。只有实际版本较低、满足可选版本条件且没有停更，客户端才会得到 update=true。当前客户端无需更新时仍展示发布流已配置的策略。版本号取自管理读回。

## 2. 按状态给客户选操作

按主规范的固定版本操作编号出题。下表只判断哪些动作可用；过滤后仍用原号，例如改强制始终为 5，取消始终为 6。恢复推荐或强制分别沿用 4、5。

先报结果，例如“Windows x64 stable 已设置 1.3.0 推荐更新。当前 1.2.0 启动时会提示，可稍后更新。” 实际回复替换为本次已核验的值。客户已在原话选定操作时直接往下走。

| 当前设置     | 给客户的选择                                             |
| ------------ | -------------------------------------------------------- |
| 推荐更新     | 查看详情、改为强制更新、取消当前更新、重新设置更新       |
| 强制更新     | 查看详情、改为推荐更新、取消当前更新、重新设置更新       |
| 仅手动可见   | 查看详情、改为推荐或强制、取消当前更新、重新设置更新     |
| 已取消／停更 | 查看详情、重新设置更新，或按客户选定的推荐／强制方式恢复 |
| 尚无记录     | 告知尚无更新，可设置第一条更新                           |
| 状态无法确定 | 给出失败项，修复后重查                                   |

**查看详情到此结束。** 给出环境/目标、客户端与发布版本、模式和适用条件、提示文案、说明、下载地址及客户端实测结果。含签名或访问凭据的完整链接放在私有状态文件，正文给该文件链接。客户选择“保持现状”或退出也直接结束。

## 3. 对话收取缺项，助手回写设置文件

助手默认运行 review。它在本地生成当前目标的受限设置文件，同时完成可以做的校验。已准备好的计划直接给客户确认；文件随计划供查看，调整值在对话回复。步骤 3 和 4 可以在同一次回复中完成。

已从客户原话或对应发布材料确定新值时，助手用 writePrivate 在任务私有目录准备事实文件，传入 --facts-file。该 JSON 含 snapshot（本次状态文件实际绝对路径）和 release（仅本次目标已确定的发布字段）。助手执行文件操作，客户无需制作此文件。客户明确取消版本适用条件时，可在 release 中将 updateCriteria 和 versionCriteria 同时设为 null，工具会在完整写入载荷中移除这两项，并在差异中列出。根据客户说的“强制”“推荐”“取消”预填完整的三个互斥布尔值；签名链接优先复用；缺失时在对话收取，回写私有文件，回执遮蔽签名。原设置文件也可继续用 review --form 校验。

```text
node cloudbase/personal/release-management.mjs review --snapshot <状态文件> --action <动作>
node cloudbase/personal/release-management.mjs review --snapshot <状态文件> --action new --facts-file <助手预填的私有文件>
```

- 改强制用 `force`，改推荐用 `recommend`，取消用 `cancel`。预填所有原字段，只切换三个互斥开关，依次为强制/提示/停更。取消使用 false/false/true，保留原记录和条件。目标与动作已明确时直接展示影响和最终计划，客户只需确认执行。当前状态已吻合或当前无更新可取消时直接告知结果。
- 重新设置当前更新用 `reset`，预填当前记录，客户只改需要变更的值；同一版本修改原记录。设置新版本用 `new`，预填应用、code 及推荐模式，复用本次已给的新版本、真实下载地址与文案。没有文案时工具拟“有新版本可用。”作为待确认默认值。无记录也可直接新设。客户只说“重新设置”时展示预填设置，请其在对话提供需要调整的字段值，并说明可保留当前版本或填写高于现有最高版本的新版本；如果换版本，逐项核对下载地址、提示及适用条件。
- review 返回 needs-input 时按 fields 在对话一次列出缺失或错误的 key；awaiting-changes 时请客户在对话指出要改的字段和值。助手将 value 回写这次生成的 form，读回后运行 review --form。

| 文件字段                                                       | 客户要填或核对的内容                                        |
| -------------------------------------------------------------- | ----------------------------------------------------------- |
| release.codeVersion                                            | 必填，真实数字点分发布版本。新发布须高于本流最高记录        |
| release.downloadUrl                                            | 必填，本版本、本平台的公网 HTTPS 下载地址                   |
| release.promptContent                                          | 必填，提示文案，1～100 字符                                 |
| release.updateContent                                          | 可选，更新说明，允许留空字符串                              |
| release.forcedUpdate、release.promptUpdate、release.stopUpdate | 必填布尔值，按所选模式预填，最多一项为 true                 |
| release.updateCriteria、release.versionCriteria                | 可选，条件操作符 ge/gt/le/lt 与比较版本须成对填写或一并移除 |

release.name、release.code 和文件关联信息由助手预填。客户不用填写管理记录 id、API 地址、请求凭据或审计字段。

## 4. 审阅差异并确认计划

```text
node cloudbase/personal/release-management.mjs review --form <现有设置文件>
```

助手收到对话值并回写后直接校验同一文件。已有 awaiting-confirmation 计划直接交付。正文先列目标、changedFields 所示差异、影响的版本和下一动作；沿用旧版下载地址发布更高版本时在同一确认中指出。附已回写的设置文件、完整私有计划链接及便于辨认的短标识。例如：“Windows x64 stable，1.3.0 由推荐改强制，符合条件的旧版本下次检查后将限制新业务。确认执行吗？” 同一条消息只有一个明确计划或清楚列出的整批计划时，客户回复“确认执行”即可。助手将该回复绑定到展示过的计划，并自行传入完整摘要。助手展示具体目标、动作、旧值→新值、会影响哪些客户端、预计结果、实际 POST/PUT 地址及记录 id（如适用）、完整私有计划链接和计划标识。特别说明改强制后符合条件的旧版本将按已接入 UI 限制新业务，取消后该流客户端再检查会收到停更。实际待测版本不受条件覆盖时也说明。摘要正文遮蔽下载凭据，用户可核对私有计划中的精确地址。保持原值时报告无需修改。客户确认该具体计划后，助手执行远端设置。不同目标分别有计划，可在一条回复中一次确认明确列出的多个计划。多平台共用一次确认时，结果也按平台列出；若某平台数据发生变化，只重新确认该平台的受影响计划。

## 5. 远端设置与验证

```text
node cloudbase/personal/release-management.mjs apply --plan <私有计划> --confirm <已获客户确认的完整计划标识>
node cloudbase/personal/release-management.mjs verify --plan <私有计划>
```

apply 写前复查快照、输入和权限绑定。同版本改配置用准确 id 的 PUT，更高新版本用 POST，取消用 PUT 停更。客户填表、查看详情、选择动作均不代替本次写入计划确认。写前发现其他人发了更高版本或改了目标记录，重新展示当前状态和差异再确认；API 仅支持全量 PUT，没有条件写锁，仍可能与同时进行的外部修改竞态。每个计划最多发起一次写入。apply 已执行写前检查与写后读回。结果为 verified 时直接交付；结果不明时助手在已确认范围内做一次 verify，只读核对，不用客户操作。持续不可用则交付回执和待核验项。表单或远端已变时自动重算受影响的差异，再请客户确认新版计划。HTTP 200 空体是写接口的正常响应。

交付每个目标的操作、变更前后、记录 id、写入状态、管理读回、实际版本的运行时结果与私有回执。若写入有响应但读回失败，分别说明已知结果和待核验项。维护流程到此结束；客户另有制品验收请求时，再按对应范围处理。
