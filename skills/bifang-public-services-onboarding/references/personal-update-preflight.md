# 第五门禁：确认计划后自动保存版本，再预检更新接口

前置条件：本次第四门禁本地实施与验收已通过，第三门禁参数和第四门禁 UI/实现证据仍有效。页面办理按[大屏自助发布](personal-release-management.md#大屏自助发布)核对实际入口。客户已在页面提交的，从回执和管理读回核对环境、应用、发布流、版本及字段，复用结果直接做本轮已授权的预检。回执缺失先只读查证，结果不明时禁止换入口重新提交。以下对话分支按“填写发布信息并本地校验 → 展示具体自动保存计划 → 客户确认 → 助手保存并读回 → 简单接口预检 → 第六步制品测试”执行。默认不让客户手动操作版本服务；客户明确选择手动或已自行发布时复用其事实。只维护规范时不读取真实凭据、不调用接口、不运行制品。

## 按范围处理

本流程涉及客户操作云端时，在当次提示逐项展开[官方页面指引](../assets/console-guides.json)中适用的 domain、routes、grant：给可点击入口、页面内位置、目标字段或操作和完成标志。

| 本次范围   | 第五门禁动作                                                                | 进入第六步的条件                                                                    |
| ---------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 仅更新     | 补齐发布信息、本地校验，确认具体计划后自动保存并读回，再做限定更新 GET 预检 | 所选目标预检通过，证据仍有效                                                        |
| 仅统计     | 更新版本配置与更新接口预检均不适用，记录依据；不索取更新密钥或下载链接      | 第四门禁通过且本门禁记不适用，可进入适用制品的真实统计测试准备                      |
| 更新和统计 | 完成与仅更新相同的确认、保存和预检；此步不发送真实统计、不检查大屏写入效果  | 所选更新目标全部预检通过；真实统计上报留第六步，不能绕过更新失败先开展联合 EXE 测试 |

未选服务保持原状；一个目标通过不代替其他本次已选目标通过。客户明确指定按平台分阶段推进时，记录本轮目标和其余待验证目标，复用仍有效的参数/UI及本地证据；不把本轮通过标成全部平台通过。没有保存授权、保存/读回未通过或预检失败，都停留第五门禁，不能用模拟结果或管理写入返回成功代替实际预检。

## 5A：填写信息、本地校验和保存计划

助手从已有接入记录、客户本轮说明和明确对应当前发布目标的材料预填。先核对发布版本、下载地址、目标和发布行为。提示文案缺失时可拟“有新版本可用。”供客户随计划确认，更新说明默认为空。无法确定的真实版本和下载地址必须由客户补齐。所有必填信息就绪时直接校验并展示具体计划；只有缺项才请客户打开文件。助手本地校验后准备精确保存计划，确认前不写入云端；确认后通过已有版本管理 API 保存，不要求客户另外打开 API 工具。此授权不包括直写数据库、上传安装包、新建后台或修改权限。

个人模式提供已有版本管理 API，已接入自助页面的后台也调用这套 API。新增使用 `POST <已确认base_url>/versions`；修改使用 `PUT <已确认base_url>/versions/<实际已有id>`，必须有该 id 的读取依据、具体变更差异和覆盖修改的授权。默认新增，不猜 id，不将新增冲突自动转成覆盖更新。

保存使用本应用的 managementWrite 凭据和准确 code 绑定（versions:write）；管理读回用 managementRead（versions:read）；运行时预检用该目标 runtime（versions:check）。对话办理时在本地受控进程注入，页面办理时由受控服务端注入，助手不在 shell 参数、日志或回复中回显原值。缺少某个必要角色时明确待补，不自动创建、扩权或用 CAM/runtime 代替。

### 给客户的配置清单

需要客户选择预检场景时，固定为 1. 发现普通更新　2. 强制更新　3. 无需更新　4. 停更。已有明确场景直接复用。

第一轮交接只列已有值和还需客户确定的发布事实。默认使用下述独立交接文件补缺项；客户主动选择手动分支时可在其管理工具填写。不要向已有严格 schema 的 integration-input.json 强塞发布字段。含签名/访问令牌的下载 URL 与凭据只放私有文件，回复仅展示无敏感部分和“本地已匹配”的结果；缺少事实明确待补，不回显密钥、摘要或完整签名链接。

### 对话收取发布字段并回写

助手先在当前任务私有目录创建或复用每个目标的 `<target>-release-handoff.json`，保留已有发布事实。只维护 Skill 时使用模拟文件。

文件结构采用 `release` 对象保存发布 body，另有 `expected_scenario` 保存预期场景。助手预填已确认的应用、目标、当前版本、服务地址、凭据来源，以及 `release.name`、`release.code` 和适用默认值；不复制密钥原值。多目标分别明确文件与目标对应关系，不让客户猜某个文件属于哪个平台。

在对话按目标列出下表中实际缺少的 key 和格式。客户只输入 value，助手回写对应文件。

| 文件中的字段路径                                                       | 客户填写内容                                                 | 必填/可选与已有值                                                                                 |
| ---------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `release.codeVersion`                                                  | 真实发布版本号；测试发现更新时必须高于正文列出的实际当前版本 | 必填；已有真实发布版本直接复用，不提供虚构版本                                                    |
| `release.downloadUrl`                                                  | 对应该平台、架构、发布版本和交付形态的真实 HTTPS 下载地址    | 必填；已有链接自动复用；缺失时在对话输入，回执遮蔽签名                                            |
| `release.promptContent`                                                | 用户看到的更新提示                                           | 必填，1～100 字符，无 HTML；已有真实文案保留                                                      |
| `release.updateContent`                                                | 更新说明                                                     | 可选，可保留空字符串                                                                              |
| `expected_scenario`                                                    | 发现普通更新、强制更新、无需更新、停更之一                   | 预检前需明确；已有场景预填，缺失时才让客户选择                                                    |
| `release.forcedUpdate` / `release.promptUpdate` / `release.stopUpdate` | 与所选场景对应的发布开关                                     | 必填 boolean；普通提示建议 false / true / false，明确这是待客户确认的默认值；更换场景时按上表调整 |
| `release.updateCriteria` / `release.versionCriteria`                   | 限定更新条件和版本                                           | 可选，默认不添加；确需限制时成对填写                                                              |

正文说明预填的 `release.name`、`release.code` 和目标/服务信息保留即可。若记录带有 `customer_completed_at` 等审计字段，由助手在自动保存及读回成功后记录；手动分支在收到实际完成反馈后记录，不让客户填写内部时间戳或证据标识。凭据文件仅作为来源，无须客户重新填写或复制密钥。

客户回复后，助手在本地回写并读回，再做字段校验。值有误时仅在对话重问对应 key；成功后展示具体保存计划。已有真实发布事实且客户选择仅检查时复用原记录。

一次给出当前目标和需要输入的 key；客户无需再次确认本地回写。远端保存继续按下段计划确认。

计划须列出：计划标识、实际目标/当前与发布版本、准确 POST 或 PUT 地址及已有 id（适用时）、全部 body 字段和可选字段省略情况、凭据来源及角色、本地校验结果、管理列表读回范围、运行时 GET 地址/次数、冲突及结果不明处理。普通文本可展示；密钥及含签名/Token 的完整下载链接仅保留私有计划，正文给对应私有文件链接。将精确目标、载荷、凭据绑定和输入证据绑定到不可变私有计划；不能只确认“自动保存”而没有可审阅内容。

## 5B：明确确认后自动保存并核验

正文请求客户确认具体计划，说明会写入版本服务；同时说明随后管理读回和限定更新 GET，不下载/安装/运行制品、不写统计。客户确认后记录原话、时间及计划标识，复核输入和凭据绑定未变，再按原计划执行。不把“修改 Skill”“已填写”“本地校验通过”当作保存授权；仅规范/本地限制持续有效，直到客户明确确认相应实际操作。修改版本、链接、文案、开关、目标、方法或 id 时重做受影响计划并确认。

使用受控 HTTPS 请求：5 秒超时、证书正常校验、拒绝重定向、限制响应体大小、无自动写入重试。计划可包含写前 `GET /versions?page=1&size=100` 及有界分页查重和写后同范围读回；此列表按凭据的 app/codes 返回，在本地仅匹配目标 code 与规范化版本，其余记录不输出、不修改。最多 100 页，页数和总数不完整或数据变化致无法确定时停止，不声称未找到。现有记录完全一致则核验复用；同 code/规范化版本内容不同则停止并展示脱敏差异，后续 PUT 必须重新确认真实 id 和新计划。不能更改更高版本以强行使测试通过。

当前 POST/PUT 成功合同为 HTTP 200 空响应，不凭空要求返回 id 或 JSON。随后管理列表必须找到唯一匹配记录，核对 id、code、版本、下载链接、清洗后文案、开关及条件；成功写入并不等于预检通过。超时、断连等结果不明时，先按已授权读回范围确认是否已保存，不能盲目重发 POST/PUT；仍不确定则记录待核验并停止。成功保存及读回后，直接执行已随计划确认的 5C，不再要求客户手动发布或再次确认同一操作。

工具执行或字段错误可在原授权内修复本地工具；写入目标/载荷变更需新确认。保存失败或冲突只输出固定错误分类和必要的脱敏差异，不打印原始响应/请求凭据。客户明确选择手动分支时才提供手动步骤，并等待其完成反馈；不强制已经选择自动保存的客户转为手动。

## 5C：限定的简单接口预检

先核对当前目标项目的真实运行版本/构建目标、第三门禁确认的 API origin/base path、code 和私有 runtime 凭据仍一致，按请求确认单构造路径，不从下载地址或管理入口推导检查 API。若请求配置或客户端实现实质变化，返回第三/第四门禁处理受影响项，而不是继续用旧证据。

默认每个已选发布目标，使用其实际待测客户端当前版本做一次 GET；若本次还需要核对升级后不再提示/强更解除，可在事先列出的预检范围内，对客户声明的目标版本再补一次版本边界 GET。不要伪造多个当前版本进行压力/遍历测试，不自动无限轮询或重试。

| 项目           | 必须核验的内容                                                                                                                                                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 请求           | `GET <已确认base_url>/versions/<编码后的code>/<编码后的实际当前版本>`；请求头 x-app-key、x-app-secret 从私有文件本地读取，Accept 默认 application/json；无 query、无 body、无 CAM/管理 Token                                                 |
| 传输           | 正常校验证书的 HTTPS；超时沿用已确认默认 5,000ms，响应读取设合理上限；不关闭 TLS 校验，不自动跟随重定向并转发凭据                                                                                                                            |
| 状态与内容     | 必须 HTTP 200 且为合同 JSON；HTML 中间页/登录页、空体、201、404 或仅 TCP/TLS 通了都不算通过                                                                                                                                                  |
| 七字段合同     | update、forcedUpdate、promptUpdate、stopUpdate 为 boolean；downloadUrl、promptContent、updateContent 为 string；核对字段、类型、长度、URL/文案约束及状态组合，按现有服务合同校验，不套用公司 POST/201/ClientToken 合同                       |
| 更新判定       | 用客户声明的 codeVersion、可选条件、三项发布开关与实际当前版本计算预期行为；与响应逐项对照。stopUpdate=true 时 update/forcedUpdate/promptUpdate 应为 false；update=false 时 forcedUpdate/promptUpdate 也应为 false，不能把普通提示和强更混用 |
| 下载链接与文案 | 在本地核对返回 downloadUrl 为合法公网 HTTPS、与客户实际配置对应；核对提示和经清洗更新内容符合本次配置。签名 URL 只在私有进程比对，正文不输出其凭据参数                                                                                       |
| 平台/架构/通道 | 核对实际目标→code→runtime app/code 绑定→预期下载地址的映射；响应没有这些字段，不能声称已从接口读回，也不能仅凭文件名判断真实安装包架构                                                                                                       |

使用受控本地 HTTP 工具或已实现服务层在所授权范围内请求；凭据仅在本地进程内读取和注入，助手不在 shell 参数、回复、工具输出或共享日志中回显原值。第三门禁的 preview 命令只生成实例，第二门禁的 plan 只预检资源，它们都不能代替本门禁真实更新 GET；不能通过启动应用/EXE 来“顺便预检”。当前本页是执行规范，不代表新增了可直接运行的一键预检命令；没有可安全执行请求的工具时标“待预检”，不能声称通过。

**此阶段不请求下载链接本身**，包括 HEAD/GET 探测；不下载包、不打开安装器、不构建/启动 EXE、不触发 GUI、不写统计、不发布版本或改云端配置。下载 URL 的格式和返回值匹配只能证明配置吻合，不能证明链接可达、包内容/平台正确、签名有效或安装成功。

当前 GET 响应也**不返回目标版本号**。codeVersion 来自客户发布交接；本次只能验证当前版本的判定、链接和文案与该声明相符，不能声称已从接口独立读回“最新版本就是 X”。补做目标版本边界 GET 仍不等于读取管理记录。服务实际选择该 code 的最高版本，若已有更高版本或条件影响结果，报告不一致，由客户核对调整，不改用管理密钥绕过。

## 失败、通过与第六步入口

401/403、404 未发布或路由不符、429、超时/TLS/重定向/HTML、字段错误、链接不匹配或更新行为不符，均记本次预检失败。只输出脱敏目标、HTTP 状态/固定错误分类、失败检查项和客户需核对的配置；不要展开含凭据/签名 URL 的响应。说明可能原因与已证实事实，不能把通用 404 武断认定为“从未发布”。

预检失败先区分保存问题、路由/鉴权问题和本地实现问题；涉及新的云端写入时展示修正计划并确认，不自动改后台。已覆盖同一目标读取的授权可复用，客户告知问题修复后重检；未完成前不轮询。请求或 UI 变化按前门禁重新确认，单纯发布事实修正不重走全部门禁。

通过条件为：

- 第四门禁通过，当前所选目标与请求证据有效，已按确认计划保存并管理读回匹配，或客户选择手动分支且已提供完整完成事实。
- 所选目标的实际更新 GET 均通过状态、合同、映射、链接和预期行为核验，无缺少或失败项。
- 结果满足本次准备测试的场景。准备测试“发现更新”时必须有真实高版本且实际 update=true；只有“无需更新/停更”结果不能冒充升级路径已就绪。客户明确选择只测无需更新场景时，可仅对该场景通过，并保留其他场景未验证。

脱敏记录至少包含：前置 confirmation_id/UI/本地验收引用、保存计划及客户确认、真实请求时间、环境与 app/code/平台/架构/通道、当前与发布版本及其证据来源、保存状态及管理读回匹配、HTTP 状态和七字段核验结果、下载地址本地比对结果、场景、失败/待补项和制品/统计边界。凭据只记来源文件与用途，不记原值或指纹。状态使用“待补发布事实 / 待确认保存计划 / 待保存 / 保存失败或结果待核验 / 已保存并读回 / 待预检 / 预检失败 / 更新接口预检通过 / 仅统计不适用”。预检通过不代表 EXE 已通过。

通过（或仅统计不适用）后直接进入 [第六步构建与制品测试](personal-artifact-testing.md)。在 5A 展示保存计划时一并说明当前目标的构建、运行、真实更新和所选统计基础验收。统计验收包括登录当前大屏，对照已填中文名核对该应用的真实指标响应和页面选择器。客户确认覆盖该范围后，不再在第五门禁结束时重复要求开始测试。客户随后明确要求直接构建并测试的授权同样复用。旧计划若明确排除制品操作则保持该限制，直到客户改变；只维护规范不运行制品。

核对实际项目、版本、架构及既有产物后，缺少制品就构建，随后启动并测试。若授权不包含下载或安装更新包，基础测试只运行本地构建的当前版本；不把打开下载页当作安装成功。第五门禁与第六步各自记录结果，未验证平台继续待验证。
