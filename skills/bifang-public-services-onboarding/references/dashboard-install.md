# 版本管理的安装与升级

客户说“新环境接入更新”“老后台增加版本管理”时，助手复用本任务的私有 resource-input.json 和已有环境记录。先只读盘点环境、版本函数、大屏函数、发布流、现有名称及路由，再交付逐项差异。仅查看当前版本或修改已发布记录走[版本管理](personal-release-management.md)。

| 环境现状                                                   | 助手办理                                                                                                                                                                                                                           |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 全新个人免费环境                                           | 按第一、二门禁准备资源。选择更新与统计，登记中文应用名、平台、架构、通道及 code。资源计划同时创建 application-version-api 与 operations-dashboard-api，会自动生成后台绑定。复用同一套登录口令。                                    |
| 已有统计大屏，整个环境没有版本服务                         | 保留大屏和统计资源，在资源文件标记 dashboard、telemetry 为 created，update 为 missing。只为实际发布目标准备版本函数、版本/审计等集合、索引、路由及运行时凭据。只选择更新且没有大屏的客户仍可使用对话发布。已有大屏待下述步骤升级。 |
| 同环境已有共享版本服务，目标应用尚未接入更新               | 先核对版本映射和大屏应用列表。目标在版本服务中尚未登记，大屏中尚未登记或其发布流为空时，按共享 extend 计划补应用、凭据、集合与索引，保留历史日活。若已有旧版大屏，再执行下述升级。                                                 |
| 两个服务都有，但没有发布页、绑定缺失或大屏未登记已有发布流 | 保留版本记录、应用 ID、发布 code、凭据和大屏口令。生成下述升级材料。先核对现有版本服务中已授权的发布流，再将缺少的映射合入大屏。                                                                                                   |
| 已有发布页并能查看目标流                                   | 直接核验登录、当前记录、实际客户端 GET，再办理本次操作。没有发布记录是有效的初始状态。                                                                                                                                             |

## 准备旧环境材料

由助手在已定位的源码仓库运行以下命令。使用当前任务私有文件的实际绝对路径。工具只读核对免费条件、目标环境及两个函数，用 GetFunctionAddress 下载并校验正在服务的原包，另生成两个新版 ZIP、逐函数完整配置和私有清单。输出短摘要中的 sha256 绑定本次计划。

```text
node cloudbase/personal/dashboard-upgrade.mjs --file <resource-input.json>
```

旧函数把中文名编进代码包且本次输入只含部分应用时，助手从当前线上大屏的 appLabels 或已核验的原包取得其他应用名称，在本任务私有目录保存 app_id 到名称的 JSON 对象，追加 `--labels-file <该文件>`。既有名称冲突先核对差异。资源工具返回 PREPARE_VERSION_RESOURCES_FIRST 时，先补版本服务的注册、凭据和集合索引，再准备大屏升级。不要用重建集合解决缺少映射。无法识别部署来源或遇到自定义函数时，先对比其源码并给单独的适配方案。

## 执行及验收

本流程涉及客户操作云端时，在当次提示逐项展开[官方页面指引](../assets/console-guides.json)中适用的 grant、functionCode、functionConfig、domain、routes：给可点击入口、页面内位置、目标字段或操作和完成标志。

1. 助手备份目标环境两个正在服务的函数包及配置，核验备份 SHA-256，与当前代码比较，列出所有将替换的代码及已有应用影响。升级工具生成的是本版标准包；客户有定制逻辑时先移植并验证。给客户私有清单链接、目标环境及函数、包摘要、变量差异和预期短暂影响。只需客户对具体计划确认一次。
2. 获得具体计划确认后，助手运行下列命令。工具在写前复查环境、旧包摘要、修改时间、原配置及私有文件摘要，按先版本服务后大屏的顺序更新并读回。私有回执记录已完成动作。同一计划最多执行一次，失败后只读盘点并为剩余差异重新准备计划。

   `node cloudbase/personal/dashboard-upgrade.mjs apply --file <resource-input.json> --plan <私有升级清单> --expected-plan <本次已确认的完整sha256>`

   对现有函数的升级需要代码更新及配置更新能力。核对实际操作者的 `scf:GetFunctionAddress`、`scf:UpdateFunctionCode`、`scf:GetFunction` 和 `scf:UpdateFunctionConfiguration`。运行时由大屏服务角色在同环境调用版本函数，先用只读详情验证调用是否成功。后台登录者无需另建账号或分配角色。

3. 对照清单中的地域、命名空间、修改时间、原配置和已备份代码摘要做写前复核。先更新 application-version-api 的代码与完整配置，等待 Active 并读回，再更新 operations-dashboard-api。保留既有角色、依赖安装方式、路由、鉴权和未修改变量。发现漂移、容量超限或状态不明时停在当前项；重新盘点已成功步骤。云写入限于已确认的目标和载荷。
4. 打开本环境的大屏登录并进入「版本管理」，逐项核验中文名、所有已登记平台、旧版本或空状态。未登录会话应被拒绝。从第五门禁已有发布或客户实际要发布的记录验收预览、确认、读回、客户端更新 GET。仅检查环境时停在查看详情，不为验收制造生产版本。已发布内容无需客户再填文件。记录实际入口、目标、已通过及待验证项，缺少真实客户端证据时标注待验证。

页面只能修改当前后台已登记的发布流。新域名、下载制品、客户端尚未实现更新检查等事项，按原接入门禁分别核对。
